# /plan — 技术方案设计

## 共通规则

1. **反问优先**：信息不足时反问，不脑补
2. **先说后做**：输出方案概要 → 用户确认 → 再写文件
3. **需求对齐**：所有输出必须关联到 PRD 中的需求编号
4. **中文输出**：所有文档和交互用中文
5. **需求接收规则**：操作员提出优化或新需求时，禁止直接执行。先自主分析（理解重述 → 优化点 → 流程 → 功能边界 → 交叉影响 → 风险点），确认后再执行
6. **功能边界意识**：方案中的每个设计决策都要分析对已有功能的影响
7. **双轨判断**：执行 `create` / `update` 前先识别交付物：
   - **研发产品轨**：交付业务代码 / 页面 / API / 数据处理 → 产出技术方案 + 任务列表（本文件前半部分流程）
   - **Skill 元开发轨**：交付 SKILL.md + 配套资源 → 产出 skill 交付方案 + `skill-map.md`（见后半部分「Skill 元开发轨」章节）
   - 拿不准 → 直接问操作员"这是研发产品任务还是 skill 元开发任务？"
8. **不压超大 skill**：元开发轨场景下不能把复杂需求压成一个超大 SKILL.md；必须按下文「拆分判定 8 条规则」检查，需要拆就拆，不能为省流程牺牲职责边界

## 前置检查

执行任何子命令前：
1. 读取 `.skills/context.json` 获取当前产品
   - 若 `context.json` 不存在或 `activeProduct` 字段为空，输出提示并终止：
     ```
     [PLAN] 未找到当前产品上下文。请先执行 /req init [产品名] 初始化产品。
     ```
2. **需求文档定位（按优先级依次查找）**：
   - **路线 A — Skill 路线**：操作员**主动**指定 SKILL.md 路径作为需求来源 → 直接以该 SKILL.md 作为需求来源
   - **路线 B — 完整流程**：检查 `.skills/{product}/docs/02-prd.md` 是否存在且状态为"已定稿" → 存在则使用
   - **都不存在**：提示操作员选择路线——「未找到需求文档。请选择：(A) 指定一个 SKILL.md 路径；(B) 先执行 /req finalize 生成 PRD」
3. **`tasks` / `check` 额外检查**：检查 `.skills/{product}/docs/plan.md` 是否存在
   - 若不存在，输出：
     ```
     [PLAN] plan.md 尚未生成，请先执行 /plan create 生成技术方案，再执行此命令。
     ```
     并终止，不继续执行
4. **项目快扫**（仅 `create` / `update` 子命令、本会话未扫过时执行）：
   - Read `package.json` / `pyproject.toml` / `pom.xml` 任一存在的清单文件
   - Glob 项目根目录结构（看 `src/`、`app/`、`server/`、`client/` 等）
   - 操作员需求涉及具体功能（"搜索"、"图表"、"支付"）→ Grep 定位是否已有相关实现
   - 输出一行：`[项目摸底] 类型:XX | 栈:XX | 已有相关:[路径]/无 → 继续`
   - 摸底结果用于：方案必须贴合现状，不能建议"引入 Redux"当项目已用 Pinia；不能凭空设计"新建目录"当目录已存在
   - `tasks` / `check` 子命令不扫（纯文档对照，不需要看代码）

## 子命令路由

| 参数 | 执行 |
|------|------|
| `create` | → 生成技术方案（研发轨） / skill 交付方案（元开发轨） |
| `tasks` | → 拆解开发任务列表（研发轨） |
| `map` | → 生成或刷新 `skill-map.md`（元开发轨） |

| `update` | → 增量更新方案（需求变更后同步，双轨通用） |
| 无参数 | → 显示当前方案状态 |

当操作员使用自然语言而非精确命令时，按以下规则映射：

| 操作员可能的表达 | 映射到 |

| "方案需要调整"、"需求变了方案怎么办" | → update |

## create — 生成技术方案

### 执行步骤

1. **读取 PRD**：`.skills/{product}/docs/02-prd.md`
2. **读取代码规范**（如存在）：`.skills/{product}/docs/standards.md`
3. **读取 Baseline**：`.skills/{product}/docs/01-baseline.md`

4. **生成技术方案**，包含：

   a. **技术选型**
   - 基于用户技术栈（默认 Vue 3 + Vite + Tailwind）
   - 列出需要的第三方库及理由
   - 标注与 PRD 技术约束的一致性

   b. **架构设计**
   - 整体架构图（ASCII 或描述）
   - 模块划分及职责
   - 数据流向
   - 关键技术决策点及理由

   c. **目录结构规划**
   - 基于技术选型的标准目录结构
   - 各模块文件归属
   - 公共资源组织

   d. **模块拆分**
   - 每个 PRD 模块对应的技术实现模块
   - 模块间依赖关系
   - 接口定义（输入/输出）

   e. **风险点标注**
   - 技术风险（性能瓶颈、兼容性问题）
   - 依赖风险（第三方库稳定性）
   - 集成风险（模块间耦合点）

5. **需求覆盖标注**：方案中的每个模块/决策旁标注关联的 REQ 编号

6. **输出方案概要**给用户确认

7. 确认后写入 `.skills/{product}/docs/plan.md`（使用模板）

8. **同步更新** `05-todo.md`：方案设计阶段标记为完成

### 输出格式

```
## 技术方案概要

技术栈：{{选型}}
模块数：{{N}} 个
覆盖需求：{{已覆盖}}/{{总数}} | 未覆盖：{{列表}} | 超出：{{列表}}

[详细方案见 .skills/{product}/docs/plan.md]

→ 确认方案？确认后可执行 /plan tasks 拆解任务
```

## tasks — 拆解开发任务列表

### 异常处理

- **plan.md 不存在**：前置检查已拦截，此处不会执行（见前置检查第4条）
- **plan.md 存在但无模块内容**：输出 `[PLAN] plan.md 内容不完整，缺少模块拆分章节，请重新执行 /plan create` 并终止
- **PRD 迭代规划缺失**：若 `02-prd.md` 中无迭代规划章节，按单阶段处理，输出提示 `[PLAN] PRD 中未找到迭代规划，将所有任务归入阶段一`

### 执行步骤

1. 读取 `.skills/{product}/docs/plan.md`
2. 读取 `.skills/{product}/docs/02-prd.md` 的迭代规划

3. 按阶段拆解任务：
   - 每个任务关联一个或多个 REQ 编号
   - 标注任务依赖关系
   - 估算任务复杂度（简单/中等/复杂）
   - 标注任务类型（前端/后端/全栈/配置）

4. 输出任务列表给用户确认

5. 确认后追加到 `.skills/{product}/docs/plan.md` 的任务列表章节

6. **同步更新** `05-todo.md`：任务拆解阶段标记为完成，阶段研发章节填充具体任务

### 任务列表格式

```
## 阶段一任务列表

| # | 任务 | 关联需求 | 类型 | 复杂度 | 依赖 | 状态 |
|---|------|---------|------|--------|------|------|
| 1 | {{任务描述}} | REQ-A-001 | 前端 | 中等 | 无 | 未开始 |
| 2 | {{任务描述}} | REQ-A-002 | 全栈 | 复杂 | #1 | 未开始 |
```

## check — 方案与需求覆盖度对比

### 执行步骤

1. 读取 `.skills/{product}/docs/plan.md`
2. 读取 `.skills/{product}/docs/02-prd.md`

3. 逐条对比：
   - **已覆盖**：PRD 中的需求在方案中有对应实现
   - **未覆盖**：PRD 中的需求在方案中没有对应实现
   - **超出需求**：方案中有内容不对应任何 PRD 需求

4. 输出覆盖度报告

### 报告格式

```
[PLAN CHECK] 方案与需求覆盖度报告

PRD 版本：vX.X | 方案版本：{{日期}}

已覆盖（N/M）：
  ✓ REQ-A-001 — 对应方案模块：{{模块名}}
  ✓ REQ-A-002 — 对应方案模块：{{模块名}}

未覆盖（K 条）：
  ✗ REQ-B-003 — PRD 中定义但方案中未体现
    → 建议：补充 {{建议}}

超出需求（J 条）：
  ⚠ 方案中包含"{{内容}}"但 PRD 未定义
    → 建议：移除或先更新 PRD

覆盖率：N/M (XX%)
```

## update — 增量更新方案

当 `/req update` 修改了需求后，用此命令同步更新技术方案。

**前置条件**：`.skills/{product}/docs/plan.md` 必须存在

**执行步骤**：

1. 读取 `02-prd.md` 最新版本，对比 `plan.md` 中引用的 PRD 版本号
2. 如果版本号一致（方案已是最新），输出提示并终止：
   ```
   [PLAN] 方案已基于最新 PRD (vX.X)，无需更新。
   ```
3. 读取 `changelog/{product}.log` 最近一次变更记录，提取变更内容
4. 分析变更对现有方案的影响：
   - 新增需求 → 方案中需追加模块/任务
   - 修改需求 → 方案中需调整对应模块设计
   - 删除需求 → 方案中需移除对应模块（标记为已废弃，不直接删除）
5. 输出更新预览，等操作员确认：
   ```
   [PLAN UPDATE] 方案更新预览

   PRD 版本：vX.X → vX.Y
   变更内容：[摘要]

   方案影响：
   - [新增/修改/废弃] 模块 A：[具体影响]
   - [新增/修改/废弃] 模块 B：[具体影响]

   → 确认更新方案？
   ```
6. 操作员确认后，编辑 `plan.md`，更新版本号引用和受影响的模块
7. 同步更新 `05-todo.md` 中的任务列表（新增/调整/标记废弃）

# Skill 元开发轨：skill 交付方案与 skill-map

> 以下章节仅在 `/plan` 工作于 **Skill 元开发轨** 时使用。研发产品轨用户跳过此区域。

## create（元开发轨）— 生成 skill 交付方案

### 执行步骤

1. **读取需求来源**：
   - `02-prd.md`、`03-features.md`
   - `01-baseline.md`（如存在）
   - 已有 `.claude/skills/*/SKILL.md`（避免重复设计）

2. **提取所有 REQ 编号、功能点、验收标准、依赖关系**

3. **判断每个功能点是否适合做成 skill**：
   - 一次性触发并产出结果 → 适合做 skill
   - 需要持续运行、长期 UI、后台队列、登录态 → 不适合直接做成 skill
   - 需要系统、页面、API、CLI、脚本、数据处理、报告工具、复杂操作承载 → 建议实现承载，同时保留 REQ 和 skill-map 映射

4. **拆分 skill**（按下文「拆分判定 8 条规则」）

5. **为多 skill 工作流选择编排方式**（按下文「编排策略三选一」）

6. **为每个拟建 skill 定义**：
   - 名称（kebab-case）
   - 类型：指令型 / 工具型 / 编排型
   - 职责（一句话）
   - 输入 / 输出
   - 依赖 skill
   - 状态文件
   - 验收方式
   - 蓝本侦察建议：标准/复杂建议 `/github-blueprint`，轻量单 skill 可跳过

7. **为需要实现承载的功能点定义**：
   - 对应 REQ
   - 实现类型：系统 / 页面 / API / CLI / 脚本 / 数据处理 / 报告工具 / 其他
   - 承载内容、输入输出、关联 skill 或工作流
   - 需同步文件：PRD / features / plan / skill-map / 相关 SKILL.md
   - 验收方式：按类型说明 UI/API/CLI/数据/报告/安全/构建/测试证据

8. **输出方案概要等用户确认**，确认后写入：
   - `.skills/{product}/docs/plan.md`（skill 交付方案）
   - `.skills/{product}/docs/skill-map.md`（PRD 功能点 → skills 映射）

9. **同步更新 `05-todo.md`**：方案设计阶段标记为完成

### 拆分判定 8 条规则

不只按步骤数拆，也按可确认产物、可复用能力、可归因边界和高成本执行点拆。当单个 skill 命中以下任意 **2 条**时，必须显式判断是否拆分；命中 **3 条以上**时强烈建议拆分，用户坚持单体时记录理由和风险：

1. 包含两个以上独立能力（如"分析/识别"和"生成/执行"混在一起）
2. 中间产物本身有价值（颜色分析、候选方案、评分结果、结构化报告）
3. 中间产物需要用户确认后才能继续
4. 失败原因来自不同阶段，混在一起会难以归因
5. 前半段可复用到其他任务
6. 后半段依赖高成本模型/API、批量执行、覆盖文件或其他高风险操作
7. 流程虽短但提示复杂、约束密集、测试样例难覆盖
8. 输入输出开始变成多个状态文件、多个中间产物或多个报告

拆分判定必须回答：为什么保持单体或为什么拆成多个 skill；中间产物是什么；谁确认；后续如何评估。

### 编排策略三选一

多 skill 工作流必须明确编排方式，不能只列 skill 名称：

| 编排方式 | 适用 | 必须说明 |
|---|---|---|
| **主 skill 编排** | 流程稳定、人工按步骤触发、需要明确顺序 | 主 skill 只做顺序、确认和状态衔接，不复制子 skill 业务逻辑 |
| **scripts/ 串接** | 有 API、文件流转、批处理，适合自动化 | 脚本路径、输入输出、错误处理 |
| **plan.md/skill-map.md 编排表** | 需求会变化、步骤需人工判断、需要可审计 | 编排表如何维护，谁负责更新 |

### skill-map.md 格式

```markdown
| REQ-ID | 功能点 | 适合做 skill | skill 名称 | 类型 | 输入 | 输出 | 依赖 skill | 状态文件 | 验收方式 | 状态 |
|---|---|---|---|---|---|---|---|---|---|---|
| REQ-A-001 | 示例功能 | 是 | example-skill | 指令型 | 用户输入 | 报告 | 无 | 无 | 输出符合 AC | planned |
```

### 状态枚举与主写入方

| 状态 | 主写入方 | 条件 |
|---|---|---|
| `planned` | `/plan create`、`/plan map` | 已生成方案映射 |
| `created` | `/create-skill` | `SKILL.md` 已创建并通过基础安全扫描 |
| `optimized` | `/darwin-skill` | 已有评分记录，或优化循环完成并保留改动 |
| `reviewed` | `/review check` | 对照 PRD、plan、skill-map 验收通过 |
| `packed` | `/pack build/check` | 已为 `reviewed`，已纳入 manifest 和 zip，且 zip 校验通过 |
| `not-skill` | `/plan create`、`/plan update` | 功能点不适合做 skill，且理由明确 |
| `deprecated` | `/plan update` | PRD 删除或废弃该功能点 |

`skill-map.md` 是元开发轨的精确状态源；`05-todo.md` 只做阶段摘要。除用户明确要求或 PRD 变更导致 `deprecated` 外，不回退已有状态。

## map — 生成或刷新 skill-map

仅在 Skill 元开发轨使用。

执行步骤：

1. 读取 `.skills/{product}/docs/plan.md` 和 `02-prd.md`
2. 根据 plan 中的 skill 拆分刷新 `skill-map.md`
3. 保留已有状态，不把 `created/optimized/reviewed/packed` 回退为 `planned`
4. 对新增功能点补新行
5. 对删除功能点标记为 `deprecated`，不直接删除历史映射

## 无参数时（`/plan`）

输出当前方案状态：

```
当前产品：{{产品名}}
方案状态：{{已创建/未创建}}
任务拆解：{{已完成/未完成}}
覆盖率：{{百分比}}

可用命令：
  /plan create  — 生成技术方案（研发轨）/ skill 交付方案（元开发轨）
  /plan tasks   — 拆解任务列表（研发轨）
  /plan map     — 生成或刷新 skill-map（元开发轨）
  /plan check   — 覆盖度检查（双轨通用）
  /plan update  — 增量更新方案（双轨通用）
```
