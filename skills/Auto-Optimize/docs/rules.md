# R1-R4 规则

## R1 — 可追溯

每轮迭代必须有对应的 git commit。

**禁止：**
- 声称"迭代了 3 轮"但没有 3 个 commit
- 声称"改了 X"但 diff 里没有对应变更
- 只在对话里说"我改了"而没有实际修改文件

**执行方式：** 每轮 Step 3 迭代结束后，如果用户允许 commit，使用格式：
```
refine(N): [改动描述] [score: X.X → Y.Y]
```

## R2 — 不虚报

没有实际执行的验证不能声称通过。

**禁止：**
- 声称"测试通过"但没有运行测试命令
- 声称"构建成功"但没有运行 `npm run build`
- 声称"没有回归"但没有做任何检查

**执行方式：**
- 能跑终端 → 必须实际运行验证命令并展示输出
- 不能跑终端 → 必须说"请手动验证"并提供具体命令

## R3 — 标准优先

Step 1 中定义的成功标准是完成的硬性门槛。自评高分不能替代。

**禁止：**
- "自评 8.5 分，可以交付了"但成功标准还有未满足的
- "差不多了"而不逐条检查成功标准
- 中途偷偷修改成功标准来降低门槛

**执行方式：**
- 终止前必须逐条确认每个成功标准的状态（通过/未通过）
- 有未满足的标准 → 继续迭代或报告给用户
- 4 轮后仍有未满足 → 列出剩余问题，询问用户决策

## R4 — 环境诚实

如实描述自己的验证能力。

**执行方式：**
- 能运行终端命令 → 必须实际运行，展示命令和输出
- 不能运行 → 不说"已验证"，改为"请运行以下命令验证：[命令]"
- 如果命令执行失败 → 展示错误输出，分析原因，不隐藏
