# /dev — 研发执行

## 共通规则

1. **需求接收规则**：操作员提出优化或新需求时，禁止直接执行。先自主分析整理（理解重述 → 优化点 → 流程 → 功能边界 → 交叉影响 → 风险点），确认后再执行
2. **功能边界意识**：每次改动都要分析对其他已有功能点的影响
3. **不虚报（R2）**：没有实际运行的验证不能声称通过。能跑就跑，不能跑就说明
4. **标准优先（R3）**：PRD 验收标准是完成的硬性门槛，自评高分不能替代
5. **可追溯（R1）**：每轮有意义的改动都应有 git commit
6. **中文输出**：所有报告和交互用中文

## 前置检查

执行任何子命令前：
1. 读取 `.skills/context.json` 获取当前产品
2. **需求文档定位（按优先级依次查找）**：
   - **路线 A — Skill 路线**：操作员指定了 SKILL.md 路径，或当前上下文中刚由 `/create-skill` 生成了 SKILL.md → 直接以该 SKILL.md 作为 PRD，跳过 /req
   - **路线 B — 完整流程**：检查 `.skills/{product}/docs/02-prd.md` 是否存在 → 存在则使用
   - **都不存在**：提示操作员选择路线——「未找到需求文档。请选择：(A) 指定一个 SKILL.md 路径作为 PRD；(B) 先执行 /req finalize 生成 PRD」
3. **会话恢复**：读取 `.skills/session.json`，如果存在且有进行中的任务，输出恢复提示
4. **待办事项告知**：读取 `.skills/{product}/docs/05-todo.md`，扫描未完成事项并汇总告知操作员
5. **项目快扫**（仅 `start` 子命令第一次调用，且本会话未扫过时执行）：
   - Read `package.json` / `pyproject.toml` / `pom.xml` / `Cargo.toml` 任一存在的清单文件
   - Glob 项目根目录看大致结构（`src/`、`app/`、`scripts/` 等）
   - 操作员需求里有具体功能词（"登录"、"图表"、"上传"等）→ Grep 在 src/ 下定位是否已有相关实现
   - 输出一行：`[项目摸底] 类型:[Vue前端/Node通用/Python/Java/Skills定义/未知] | 栈:[Vue3+Vite+Tailwind / FastAPI / ...] | 已有相关:[文件路径,...]/无 → 继续`
   - 同会话内再次调用 /dev 子命令时跳过此步

### 会话恢复（session.json）

新会话启动时，如果 `.skills/session.json` 存在且 `activeTask` 不为空，输出恢复提示：

```
[会话恢复] 检测到上次未完成的工作

任务：[REQ-ID] [描述]
复杂度：[级别]
进度：[当前步骤]
上次操作：[lastAction]
已确认的决策：
  - [决策1]
  - [决策2]

→ 输入 /dev resume 继续上次任务
→ 输入 /dev start [其他任务] 切换到新任务（上次进度保留）
→ 输入 /dev abandon 放弃上次任务
```

**session.json 结构**：

```json
{
  "activeTask": {
    "reqId": "REQ-A-003",
    "description": "用户搜索功能",
    "complexity": "标准级",
    "step": "编码中",
    "phase": "/dev start → 编码",
    "iteration": 2,
    "decisions": [
      "方案A：使用 Fuse.js 做前端模糊搜索（已确认）"
    ]
  },
  "pendingConfirmations": [],
  "lastAction": "迭代精炼第2轮，修改了搜索权重算法",
  "updatedAt": "2026-04-15 14:30"
}
```

**写入时机**（各步骤自动更新 session.json）：

| 触发点 | 写入内容 |
|-------|---------|
| `/dev start` | 创建 activeTask，记录任务信息和复杂度 |
| 操作员确认决策 | 追加到 decisions 数组 |
| 迭代精炼每轮 | 更新 iteration 和 lastAction |
| `/dev done` 通过 | 清空 activeTask（任务完成） |
| `/dev abandon` | 清空 activeTask（任务放弃） |
| 需求分析确认 | 更新 step 为"方案已确认" |
| 编码开始 | 更新 step 为"编码中" |
| 自测开始 | 更新 step 为"自测中（第N关）" |

**读取规则**：
- 新会话首次调用 `/dev` 时读取并输出恢复提示
- 同一会话内不重复输出（已恢复过就不再提示）
- `session.json` 不存在或 activeTask 为空 → 跳过恢复，正常执行

### 待办事项告知格式

每次 `/dev` 任意子命令执行前，输出当前待办概览：

```
[待办提醒] 当前产品：[产品名]

未完成事项：N 项
  ⬜ [REQ-ID] [任务描述] — 状态：[未开始/进行中]
  ⬜ [REQ-ID] [任务描述] — 状态：[进行中（迭代 2）]
  🐛 [BUG-ID] [bug 描述] — 来源：push 健康扫描
  💡 [OPT-ID] [优化建议] — 来源：push 健康扫描

→ 继续执行 /dev [子命令]
```

**规则**：
- 只展示未完成项，已完成的不显示
- bug 和优化建议按优先级排序（高 → 中 → 低）
- 如果无未完成事项，输出"✓ 当前无待办事项"后直接执行子命令
- **静默规则**：如果本次会话中已告知过且 `05-todo.md` 无新变化，不重复输出
- 告知后不阻塞，直接继续执行操作员请求的子命令

## 复杂度自动分流

在 `/dev start` 时自动判定任务复杂度，决定后续流程的简繁程度。

### 判定规则

**根据操作员的需求描述来预判**，不需要先分析代码：

| 级别 | 怎么判断（看描述） | 示例 |
|------|-----------------|------|
| **轻量级** | "加个XX"、"优化一下"——涉及局部调整，改动对象是某个组件/函数，需要理解局部上下文但影响范围基本能判断 | 小 bugfix、调整某个组件的交互、优化某个函数 |
| **标准级** | "新增XX功能"、"实现XX"——涉及完整功能点，需要理解业务逻辑，对应 PRD 中的某个 REQ | 新功能开发、功能增强、实现某个需求 |
| **重量级** | "重构"、"重新设计"、"新增XX模块"——涉及多模块或架构层面，需要全局分析才能确定影响范围 | 架构重构、新模块、跨模块改动、破坏性变更 |

**判断原则**：大概能判断影响范围 → 轻量级。需要分析才知道影响多大 → 标准级。要全局评估 → 重量级。拿不准时往高一级走。

### 不同级别的流程差异

```
                        轻量级          标准级          重量级

需求分析 + 方案确认      ✓ 必须走        ✓ 必须走        ✓ 必须走
编码                    ✓              ✓              ✓ + 多方案探索
自测闭环                第1关+第2关      4关全过          4关全过
安全检查（commit 前）    ✓ 必须走        ✓ 必须走        ✓ 必须走
commit 前置测试          ③已有回归       ①②③全跑        ①②③全跑
commit 后文档同步        延迟到 push      立即执行         立即执行
push 前置测试           ⑥极端环境       ④⑤⑥全跑        /dev done 时已跑④⑤⑥
push 后健康扫描          仅扫描变更文件    全量扫描         全量扫描
```

### 操作员覆盖

- `/dev start --full [任务]`：无论判定结果如何，强制走完整（重量级）流程
- 判定结果会在范围锁定中输出，操作员可以手动调整

### 判定输出

```
[复杂度判定] 轻量级

判定依据：操作员描述为局部调整，影响范围可预判
关联需求：无新增 REQ
预估影响：当前组件内部

→ 自测走快速模式（第1关+第2关）
→ 文档同步延迟到 push
→ 如需完整流程，使用 /dev start --full
```

## 子命令路由

| 参数 | 执行 |
|------|------|
| `start [任务]` | → 开始任务（加载上下文 + 复杂度判定） |
| `start --full [任务]` | → 强制走完整（重量级）流程 |
| `resume` | → 恢复上次中断的任务（读取 session.json） |
| `abandon` | → 放弃当前进行中的任务（清空 session.json） |
| `done` | → 完成当前任务（自测闭环 4 关，全过才能结束） |
| `done --quick` | → 快速完成（只跑第1关 + 第2关） |
| `done --full` | → 轻量级任务强制走完整4关 |
| `check` | → 手动需求对齐检查（读取 PRD + baseline 完整对比） |
| `verify` | → 单独跑第1关：当前功能验证 |
| `regression` | → 单独跑第2关：回归影响排查 |
| `maintain` | → 单独跑第3关：可维护性检查 |
| `sync` | → 单独跑第4关：文档同步确认 |
| `progress` | → 查看整体开发进度 |
| `drift` | → 查看累计偏离记录 |
| `impact [文件/模块]` | → 变更影响分析 |
| `refactor [模块]` | → 启动重构任务 |
| `refactor --resume` | → 恢复未完成的重构 |
| `test` | → 手动触发测试（默认跑全部 ⓪+①-⑥） |
| `test --commit` | → 只跑 commit 前测试（⓪+①②③） |
| `test --push` | → 只跑 push 前测试（⓪+④⑤⑥） |
| `test --item N` | → 先跑⓪ + 只跑指定测试项（N=1-6）|
| `test --item 0` | → 只生成业务画像（不跑后续测试）|
| `test --security` | → 只跑安全相关（⓪+⑤+⑥鉴权部分+/health 维度7） |
| `test --no-context` | → 跳过⓪，用通用模板兜底（不推荐）|
| 无参数 | → 显示当前任务状态和帮助 |

## start — 开始任务

### 执行步骤

1. **加载任务上下文**：
   - 读取 `02-prd.md` 中对应需求编号的验收标准
   - 读取 `03-features.md` 中的功能规格
   - 读取 `.skills/{product}/docs/plan.md` 中的任务详情
   - 读取 `.skills/{product}/docs/standards.md`（如存在）加载代码规范

2. **【Skill 路线专属】功能→页面映射**（仅路线 A 执行，路线 B 跳过此步）：

   当 SKILL.md 作为 PRD 时，**必须先完成功能映射，确认后才能进入编码**。

   #### 核心原则

   > **SKILL.md 描述的是要交付给客户的功能，不是关于这个 Skill 本身的信息。**
   > 页面要实现的是 SKILL.md 里定义的「输入→处理→输出」能力，让客户能通过页面使用这个功能。
   > **严禁**把 Skill 的测试数据、评估分数、Darwin 结果、开发过程日志等作为页面内容展示。

   #### 映射步骤

   **步骤 A — 从 SKILL.md 提取功能三要素**：

   逐章节读取 SKILL.md，提取：

   | 要素 | 从哪里提取 | 提取什么 |
   |------|-----------|---------|
   | **输入项** | "执行流程"中的前置条件、参数、用户需要提供的内容 | 每个输入的名称、类型（文本/文件/选择/数值）、是否必填、校验规则 |
   | **处理逻辑** | "执行流程"中的步骤描述、判断条件、规则 | 每个步骤做什么、调用什么、判断标准 |
   | **输出结果** | "输出规范"或流程末尾的输出格式 | 输出的数据结构、展示形式、状态分类 |

   **步骤 B — 映射为页面组件**：

   将三要素翻译为具体的前端组件和后端接口：

   ```
   [SKILL→PAGE 映射表]

   ━━━ 输入层（用户在页面上操作的部分）━━━
   | SKILL 输入项 | 页面组件 | 组件类型 | 校验规则 |
   |-------------|---------|---------|---------|
   | [输入1名称] | [组件名] | input/upload/select/textarea | [必填/格式/大小限制] |
   | [输入2名称] | [组件名] | ... | ... |

   ━━━ 处理层（后端/API 做的事）━━━
   | SKILL 处理步骤 | API 端点 | 处理方式 | 依赖 |
   |---------------|---------|---------|------|
   | [步骤1] | POST /api/xxx | [Claude API / 本地逻辑 / 第三方] | [需要什么] |
   | [步骤2] | ... | ... | ... |

   ━━━ 输出层（页面展示结果的部分）━━━
   | SKILL 输出项 | 页面组件 | 展示形式 | 状态处理 |
   |-------------|---------|---------|---------|
   | [输出1] | [组件名] | 表格/卡片/报告/图表 | 加载中/成功/失败/空 |
   | [输出2] | ... | ... | ... |
   ```

   **步骤 C — 自检清单（强制执行）**：

   映射表输出后，逐条自检：

   | # | 检查项 | 不通过处理 |
   |---|--------|-----------|
   | 1 | 页面上的每个输入组件，是否都能在 SKILL.md 的"执行流程"中找到对应的输入要求？ | 多余的删掉，缺少的补上 |
   | 2 | 页面上展示的每个输出，是否都是 SKILL.md 定义的功能产出？ | 如果展示的是测试数据/评估结果/开发日志 → **立即删除，重新映射** |
   | 3 | 处理层是否覆盖了 SKILL.md 中所有处理步骤？ | 遗漏的补上 |
   | 4 | 页面交互流程是否与 SKILL.md 的执行流程一致？ | 顺序不对的调整 |
   | 5 | 客户能否通过这个页面完成 SKILL.md 描述的完整功能？ | 不能 → 补充缺失环节 |

   **步骤 D — 等操作员确认映射表**，确认后才进入后续步骤。

   #### 反面示例（严禁出现）

   ```
   ✗ 错误做法：
     SKILL.md 定义了"市场同款判断"功能
     → 页面展示了 Darwin 评分 78 分、测试 prompt 结果、Skill 结构分析
     → 这是在展示"关于这个 Skill 的数据"，不是实现功能

   ✓ 正确做法：
     SKILL.md 定义了"市场同款判断"功能
     → 页面有：图片上传区 + 产品名输入框 + 搜索按钮
     → 点击后调用 API 执行同款匹配逻辑
     → 结果区展示匹配到的同款产品列表（图片、相似度、来源）
   ```

3. **提取任务摘要**（用于后续编码时自行对照）：
   - 当前任务的验收标准（逐条）
   - 当前任务的功能边界（与哪些其他功能有交叉）
   - 不能被破坏的已有功能列表

3. **复杂度判定**（继承 Auto-Optimize）：

   **多方案探索** — 复杂任务：
   - 新建模块/组件
   - 架构层面调整
   - 涉及 3+ 文件的重构
   - 存在多种合理实现路径

   **单路径执行** — 简单任务：
   - 实现路径明确
   - 在现有模块上扩展
   - 改动范围可控

4. **输出范围锁定**：

```
## 范围锁定

- **任务**：[REQ-ID] [任务描述]
- **复杂度**：多方案探索 / 单路径执行
- **影响文件**：[预计修改的文件]
- **成功标准**（来自 PRD 验收标准）：
  1. [AC-1]
  2. [AC-2]
- **回归守护**：[不能被破坏的已有功能]
- **功能边界**：[与其他功能的交叉点]
- **变更白名单**（只允许动这些文件/目录）：
  - [文件/目录 1]
  - [文件/目录 2]
- **变更黑名单**（绝对不动）：
  - [不相关模块/文件]
- **已加载规范**：
  - [✓/—] 代码规范（standards.md）
```
> 未加载时不提醒。

5. **多方案探索 时额外执行**：
   - 生成 2-3 个方案对比（只写描述，不写代码）
   - 每个方案标注优劣势和影响文件
   - 选定方案并记录理由

6. **更新 `05-todo.md`**：标记任务为"进行中"

## 编码过程中的行为规则

`/dev start` 之后进入编码阶段，在此期间 **自行** 遵守以下规则（不依赖其他 Skill）：

### 变更范围监控

编码过程中，严格遵守 `/dev start` 输出的变更白名单/黑名单：

1. **每次修改文件前**，检查该文件是否在白名单内
2. **不在白名单内时**：
   - 立即停止编码
   - 向操作员说明："需要修改 [文件名]，原因是 [原因]，这不在原定范围内，是否允许？"
   - 操作员确认 → 将该文件追加到白名单，继续编码
   - 操作员拒绝 → 寻找不超出范围的替代方案
3. **禁止的行为**：
   - 顺手重构白名单外的代码
   - 修改白名单外文件的 import/export
   - 调整白名单外文件的样式、命名、格式
   - 以"改进"、"优化"、"统一风格"为由修改不相关文件

检测到超范围操作时输出：
```
[偏离提醒 - 变更范围溢出]

白名单：[已列出的文件]
试图修改：[文件名]
原因：[为什么觉得需要改]

→ 等待操作员确认后再继续
```

### 功能蔓延检测

写代码和讨论时，持续对照任务摘要中的验收标准：
- 如果正在实现的内容**不在当前任务的验收标准中** → 停下来提醒操作员
- 如果讨论的方向**属于其他 REQ 编号的范围** → 指出并建议先完成当前任务
- 如果出现"顺便做一下" → 拒绝，建议作为独立任务处理

检测到时输出：
```
[偏离提醒 - 功能蔓延]

当前任务：[REQ-ID] [描述]
检测到：正在 [偏离内容]
原因：不属于当前任务验收标准

→ 建议回到当前任务，或先 /req update 调整排期
```

### 实现偏差检测

写代码时，对照验收标准中的具体描述：
- 数据格式、字段命名、交互方式是否与 PRD 定义一致
- 错误处理方式是否与需求一致

检测到时输出：
```
[偏离提醒 - 实现偏差]

PRD 要求：[原文]
当前实现：[实际情况]
→ 需修正
```

### 偏离记录

所有检测到的偏离记录到 `.skills/guard/{product}.log`：

```
[YYYY-MM-DD HH:MM] SCOPE_CREEP | REQ-A-001 | 描述 | 处理方式
```

## 迭代精炼（多方案探索 任务的编码阶段）

继承 Auto-Optimize 的 Step 3：

### 每轮流程

1. 明确本轮要解决的问题
2. 做一个聚焦改动（一处，不是三处）
3. 跑验证：构建/测试/功能检查
4. 评估结果
5. 结果好 → 保留并 commit；结果差 → 回滚
6. 输出本轮小结

### 小结格式

```

- **本轮改动**：[一句话]

```

### 终止条件

1. 成功标准全部满足 → 进入 `/dev done`
2. 4 轮仍未满足 → 报告剩余问题，询问操作员
3. 禁止仅凭"感觉差不多"终止

### commit 格式

```
feat(REQ-A-001): [改动描述]
```

优化迭代时：
```
refine(N): [改动描述]
```

## done — 自测闭环

**4 关全过才能标记任务完成。顺序执行，前面不过后面不跑。**

### 第1关：当前功能验证

1. 读取当前任务的 PRD 验收标准
2. 逐条验证是否满足：
   - 能运行验证命令的 → 必须实际运行
   - 需要浏览器验证的 → 提示操作员检查，等确认
   - 不能运行的 → 明确说明，给出验证命令
3. 如果是优化任务，额外验证优化效果（前 vs 后指标对比）
4. UI 相关额外检查：
   - 页面是否正常打开（无白屏、无报错）
   - 文字是否存在乱码/错位
   - 亮暗主题下是否正常（如适用）
5. **【Skill 路线专属】功能映射回验**（仅路线 A 执行）：
   - 回读 start 阶段确认的「功能→页面映射表」
   - 逐行检查：页面实际实现是否与映射表一致
   - 重点检查：
     - 页面上是否存在映射表中没有的"多余内容"（测试数据、评估结果、Skill 元信息等）→ 发现即标记 ✗
     - 映射表中的每个输入组件是否都已实现且可交互
     - 映射表中的每个输出展示是否都是功能产出而非开发过程数据
   - 任何一项不通过 → 第1关整体不通过，必须修复后重跑

输出：
```
[自测 - 第1关] 当前功能验证 | [REQ-ID]

  [✓/✗] AC-1：[条件] — [验证方式] — [结果]
  [✓/✗] AC-2：[条件] — [验证方式] — [结果]
  [✓/✗] UI 检查：页面正常 / 无乱码

结论：N/M 通过
```

### 第2关：回归影响排查

1. 获取本次改动涉及的所有文件（git diff --name-only 或手动列出）
2. 通过 `.skills/tracemap/{product}.json`（如存在）找出这些文件关联的其他需求
3. 排除当前任务本身
4. 对剩余的已实现功能逐个检查验收标准是否仍满足
5. 无直接文件依赖的功能可跳过

输出：
```
[自测 - 第2关] 回归影响排查 | [REQ-ID]

本次改动文件：[N 个]
受影响的已实现功能：[M 个]

  [✓/✗] [REQ-ID] [功能名] — [影响路径] — [结果]

结论：M/M 通过 / N 个需修复
```

### 第3关：代码可维护性检查

逐项检查本次改动涉及的文件：

| # | 检查项 | 通过条件 | 具体检查方式 |
|---|--------|---------|------------|
| 1 | 模块边界清晰 | 不与其他模块交叉耦合 | `Grep` 搜索 import 语句，检查是否引用了不相关模块的内部实现（非公开 API） |
| 2 | 接口契约明确 | 输入/输出有明确定义 | `Read` 函数签名，检查 Props/参数是否有类型定义或 defineProps 声明 |
| 3 | 依赖方向合理 | 无循环依赖 | `Grep` 双向搜索 import：A→B 存在时检查 B→A 是否也存在 |
| 4 | 副作用可控 | 数据库/网络操作集中在 service 层 | `Grep` 搜索 `fetch`/`axios`/`api.` 调用，检查是否出现在组件文件中（应在 composable/service 中） |
| 5 | 配置可外部化 | 无硬编码魔法值 | `Grep` 搜索数字字面量（排除 0/1）和字符串字面量 URL/端口，检查是否应抽为常量或配置 |
| 6 | 错误可追踪 | 错误信息包含操作、参数、原因 | `Grep` 搜索 `catch` 块和 `console.error`，检查错误信息是否只有泛化描述 |
| 7 | 可独立测试 | 核心逻辑不依赖完整应用启动 | `Read` 核心函数，检查是否依赖全局状态（window/document/store）而非参数注入 |

输出：
```
[自测 - 第3关] 可维护性检查 | [REQ-ID]

  [✓/✗] 模块边界：[结论]
  [✓/✗] 接口契约：[结论]
  ...

可维护性得分：N/7
```

### 第4关：文档同步确认

检查并更新:
- `05-todo.md`:任务状态更新为"已完成"
- `03-features.md`:功能状态更新为"已实现"
- `.skills/tracemap/{product}.json`:需求↔代码映射更新
- `04-user-guide.md`:如果本功能已通过验收,补充操作说明

输出:
```
[自测 - 第4关] 文档同步 | [REQ-ID]

  [✓/✗] todo.md 状态更新
  [✓/✗] features.md 状态更新
  [✓/✗] tracemap 映射更新
  [✓/✗] user-guide 操作说明(如需)

结论:N/N 已同步
```

### 总报告

```
[DEV DONE] 自测闭环总报告 | [REQ-ID]

  第1关 功能验证：  [✓/✗] (N/M)
  第2关 回归排查：  [✓/✗] (N/M)
  第3关 可维护性：  [✓/✗] (N/7)
  第4关 文档同步：  [✓/✗] (N/N)

  [✓ 全部通过 → 任务完成]
  [✗ 未通过 → 列出修复项，修复后重新 /dev done]
```

**硬性规则**：
- 任何一关未通过，任务不能标记完成
- 修复后必须重新 `/dev done`，不能手动跳过
- `/dev done --quick` 只跑第1关+第2关（开发中间态快速验证用）
- **轻量级任务自动走 `--quick`**：如果 `/dev start` 时判定为轻量级，`/dev done` 默认只跑第1关+第2关，无需手动加 `--quick`
- 轻量级任务如需完整自测，使用 `/dev done --full` 覆盖

### 与测试项（⓪+①-⑥）的衔接

自测闭环的 4 关与测试项（⓪+①-⑥）是**两套独立体系**，衔接规则如下：

| 阶段 | 跑什么 | 为什么 |
|------|-------|--------|
| `/dev done` 进行中 | 第1-4关（功能/回归/可维护/文档同步）| 验证当前任务是否"真的做完了" |
| `/dev done` 通过 → commit 触发 | ⓪（构建业务画像）+ ①②③ | 用画像喂给 ①②③，发现业务规则违反 |
| commit 通过 → push 触发 | ⓪（复用或重建）+ ④⑤⑥ | 深度端到端 + 安全 + 极端环境 |

**重量级任务特例**：`/dev done` 通过后，**立即提前跑 ⓪+④⑤⑥**（避免 push 时才发现重大问题卡住发布）。规则见第 1310 行 push 前置测试执行条件表。

**补充**：done 第1关的"PRD 验收标准逐条验证"**不等同于**⓪的"AC 反推衍生场景"——第1关验证的是 PRD 写明的标准，⓪反推的是基于 AC 的边界/异常衍生场景。两者互补，不重叠。

## commit/push 前置安全检查

**触发时机**：`/dev done` 第4关通过后、执行 git commit 之前，自动执行以下检查。任何一项不通过则**阻止 commit**，修复后重新检查。

### 第1项：敏感文件拦截

扫描 `git add` 暂存区中的文件，拦截以下类型：

| 拦截规则 | 匹配模式 | 处理 |
|---------|---------|------|
| 环境变量文件 | `.env`、`.env.*`（`.env.example` 除外） | 阻止，提示加入 `.gitignore` |
| 密钥/证书文件 | `*.pem`、`*.key`、`*.p12`、`*.pfx`、`*.jks` | 阻止 |
| 凭证文件 | `credentials.json`、`serviceAccount*.json`、`*-secret.json` | 阻止 |
| 配置泄露 | `*.conf` 中包含 password/secret/token 字段 | 阻止，提示提取到环境变量 |

### 第2项：.skills/ 目录拦截

`.skills/` 是项目管理文档目录，**不得提交到 git 仓库**。

- 检查暂存区是否包含 `.skills/` 下的任何文件
- 如果包含 → 阻止，提示将 `.skills/` 加入 `.gitignore`
- **首次 commit 时**：主动检查 `.gitignore` 是否已包含 `.skills/`，未包含则自动添加

### 第3项：前端暴露检查

扫描暂存区中**前端可访问路径**（`public/`、`static/`、`dist/`、`src/assets/`）下的文件：

| 检查项 | 匹配条件 | 处理 |
|-------|---------|------|
| 说明性文档暴露 | `public/` 或 `static/` 下的 `.md`、`.doc`、`.docx`、`.pdf` 文件 | 阻止，提示移到后端或 `.skills/` |
| API 密钥硬编码 | 前端代码中匹配 `(api[_-]?key\|secret\|token\|password)\s*[:=]\s*['"][^'"]{8,}` | 阻止，提示走后端代理 + 环境变量 |
| Prompt 模板暴露 | 前端路径下包含 prompt 模板文件（`*prompt*`、`*system-message*`） | 阻止，提示迁到后端内置 |

### 第4项：.gitignore 完整性检查

首次 commit 或检测到缺失时，确保 `.gitignore` 至少包含：

```
# Skills 项目管理文档（不入仓库）
.skills/

# 环境变量
.env
.env.*
!.env.example

# 密钥和凭证
*.pem
*.key
*.p12
credentials.json
```

如果缺失，**输出建议并追加**（需操作员确认）。

### 第5项：变更范围校验

对比暂存区文件与变更白名单（`/dev start` 或微型任务确认时列出的白名单）：

1. 获取暂存区文件列表（`git diff --cached --name-only`）
2. 对比白名单：
   - 全部在白名单内 → ✓ 通过
   - 存在白名单外的文件 → ✗ 列出超出范围的文件，要求操作员确认
3. 操作员确认"确实需要改" → 通过，追加到白名单
4. 操作员确认"不该改" → 还原该文件（`git checkout -- [file]`），重新检查

**适用范围**：所有任务级别（含微型任务）。微型任务在"简要确认"阶段列出的文件即为白名单。

### 检查输出格式

```
[安全检查] commit 前置检查

  [✓/✗] 敏感文件拦截：[结果]
  [✓/✗] .skills/ 拦截：[结果]
  [✓/✗] 前端暴露检查：[结果]
  [✓/✗] .gitignore 完整性：[结果]
  [✓/✗] 变更范围校验：[N 个文件全部在白名单内 / 发现 M 个超出范围的文件]

结论：[全部通过 → 进入 commit 前置测试] / [N 项未通过 → 修复后重新检查]
```

## test — 手动测试

### 定位

`/dev test` 允许在不走 commit/push 流程的情况下，手动触发任意测试项。测试逻辑完全复用 commit/push 前置测试的定义（①-⑥），只是触发方式不同。

### 前置检查

1. 检测项目代码是否存在（空项目终止）
2. 各测试项的前置条件同 commit/push 前置测试：
   - ① 需要测试框架（无则降级静态扫描）
   - ③ 需要测试框架（无则跳过）
   - ④ 需要 Playwright + dev server
   - ⑤ 需要 dev server / 后端服务

### 参数路由

| 参数 | 执行范围 |
|------|---------|
| 无参数 | ⓪ + ①②③④⑤⑥ 全跑 |
| `--commit` | ⓪ + ①②③ |
| `--push` | ⓪(复用或重建) + ④⑤⑥ |
| `--item N` (N=1-6) | 先跑⓪ + 只跑第 N 项 |
| `--item 0` | 只跑第0项（生成业务画像，不跑后续测试）|
| `--security` | ⓪ + ⑤ + ⑥中鉴权部分 + 调用 `/health scan --dim 7` |
| `--no-context` | 跳过第0项（紧急情况下用通用模板兜底，不推荐）|

### 执行流程

1. 解析参数确定测试范围
2. **如果范围包含⓪**：执行第0项构建业务画像，输出后等待操作员确认（除非 `--item 0`，确认后继续）
3. 输出测试范围预览，等操作员确认：

```
[DEV TEST] 测试范围确认

将执行以下测试项：
  ⓪ 测试上下文构建（业务画像）
  ① 边界输入测试（临时生成，含业务边界值）
  ② 接口契约测试（静态分析，含业务字段语义）
  ③ 已有测试回归
  ④ E2E 用户场景测试（Playwright，含业务链路）
  ⑤ API 安全测试（node 脚本，含业务权限）
```

### 与 commit/push 流程的关系

- `/dev test` 是独立入口，跑完**不会触发 commit 或 push**
- 如果 test 通过后紧接着 commit/push，commit/push 前置测试可以**跳过已通过的项**（10分钟内有效）
- `/dev test` 的结果不写入任何文档，只输出到对话
- 失败项的处理同"测试问题反馈链路"（三分类：代码Bug/需求盲区/设计缺陷）

## 测试上下文构建（前置）

**定位**：所有测试项（①-⑥）执行前的统一前置，输出一份"业务画像"，让后续测试用例的生成不再是空套通用模板，而是基于本次改动的真实业务语义、PRD 约束、调用关系和历史教训。

**为什么需要**：通用测试模板（null/超长/XSS）能发现"代码不健壮"，但发现不了"业务规则错了"。AC 写"积分不足时提示"，通用模板永远不会构造"刚好等于阈值"和"差1分"的用例；guard log 里记录的"并发扣减导致余额为负"也不会自动变成回归用例。第0项就是补这个缺口。

### 触发时机与复用规则

| 时机 | 执行 |
|------|------|
| commit 前置测试开始时 | 跑第0项，输出业务画像，喂给①②③ |
| push 前置测试开始时 | 检查 10 分钟内是否有 commit 时跑过的画像缓存 → 有则复用，无则重跑，喂给④⑤⑥ |
| `/dev test` 触发时 | 跑第0项，喂给被选中的测试项 |

**画像缓存位置**：`.skills/{product}/test-context-cache.json`，包含 `generatedAt` 时间戳和完整画像内容。push 时如果缓存存在且距 commit 时间 < 10 分钟，直接复用。

### 任务级别矩阵

| 任务级别 | 第0项执行范围 |
|---------|--------------|
| 微型 | 跳过（不跑测试） |
| 轻量级 | 简化版：只读 AC + 改动文件清单，不做上下游分析 |
| 标准级 | 完整跑：AC + 上下游 + tracemap + guard log |
| 重量级 | 完整跑 + 跨模块上下游追踪（递归 1 层） |

### 执行步骤

#### 步骤1：读取改动范围

- `git diff --cached --name-only`（commit 前）或 `git diff --name-only HEAD~1 HEAD`（push 前增量）获取改动文件
- 解析每个文件中本次改动涉及的函数/组件/API（用 `git diff` 提取 hunk 范围内的标识符）

#### 步骤2：关联 PRD 验收标准（AC 反推）

- 读取 `.skills/context.json` 获取当前产品
- 读取 `.skills/{product}/docs/02-prd.md`，找到与本次改动关联的 REQ-ID 的 AC 列表
- 关联方式：commit message 中的 REQ-ID 优先；没有则通过 `tracemap.json` 反查改动文件关联的 REQ
- 对每条 AC，**反推 3 类衍生场景**：

| 衍生场景 | 怎么推 | 示例（AC："积分不足时显示提示"） |
|---------|--------|-------------------------------|
| 正常路径 | AC 描述的常规走法 | 积分=100，扣50 → 成功 |
| 边界路径 | AC 阈值的"刚好等于/差1/正好为0" | 积分=50 扣50 / 积分=49 扣50 / 积分=0 |
| 异常路径 | AC 描述的失败态 + 反方向值 | 积分=负数 / 用户已注销 / 并发扣减 |

#### 步骤3：上下游与副作用分析

对改动文件的每个改动点：
- **上游**：`Grep` 调用方（搜索函数名/组件名/路由路径），列出前置触发场景
- **下游**：`Read` 函数体，提取它调用的 API/数据库/缓存/消息队列
- **副作用**：标识写操作的方向（DB 写 / 缓存失效 / 文件写 / 网络请求 / 状态机变更）

#### 步骤4：历史坑提取（guard log）

- 读取 `.skills/guard/{product}.log`
- 过滤与本次改动文件/REQ-ID 相关的偏离记录
- 提取"曾发生过的问题"，作为回归用例蓝本（重点关注 IMPL_DRIFT 和 TEST_SKIP 类型）

#### 步骤5：业务边界值生成

综合 AC 反推 + 上下游签名，对每个改动函数/接口的关键参数列出：
- 参数名 + 业务含义（如 `amount` = 扣减金额）
- 业务边界值序列（不是技术边界，是业务语义边界）
- 标注每个值对应的预期业务行为

### 第0项输出格式

```
[测试上下文] 本次改动业务画像

  关联需求：[REQ-IDs] / 无关联（通过 tracemap 也未匹配）
  改动文件：N 个
    - [文件路径] — 改动函数/组件：[名称列表]

  业务语义：
    [一句话描述这次改动在做什么业务行为]

  关键 AC（场景蓝本）：
    AC-1：[原文]
       → 正常：[场景描述]
       → 边界：[场景描述]
       → 异常：[场景描述]
    AC-2：...

  上下游：
    上游调用方：[文件:行号 + 触发场景]
    下游依赖：[API/DB/Cache/MQ 列表]
    副作用方向：[写库 / 缓存失效 / 状态变更 / ...]

  业务边界值（→ 注入第①项）：
    [参数名]：[值1, 值2, ...] — 含义：[每个值代表什么业务情况]

  历史坑（→ 注入②③④⑤⑥）：
    📌 [日期] [类型] [描述] — 来源：guard log
    📌 [日期] [类型] [描述] — 来源：guard log
    （无历史坑则输出"无相关历史记录"）

  画像已缓存至 .skills/{product}/test-context-cache.json，10 分钟内 push 测试可复用。
```

### 降级规则

| 缺失项 | 降级策略 |
|-------|---------|
| 无 PRD（02-prd.md 不存在）| 跳过步骤2，业务画像中标注"无 PRD，仅基于代码语义" |
| 无 tracemap | 跳过通过文件反查 REQ 的步骤，仅依赖 commit message |
| 无 guard log | 步骤4 输出"无历史记录"，不阻断 |
| 无关联 REQ | 仅基于代码上下文生成画像，AC 反推部分输出"未关联 AC，使用代码签名兜底" |

### 失败处理

第0项**不会失败**，它只输出画像。如果画像生成过程中读文件失败 → 输出对应部分的"读取失败"提示，但不阻断后续测试。后续测试项遇到画像中标注"无"的部分时，回落到原有通用模板逻辑。

## commit 前置测试

**触发时机**：安全检查全部通过后、执行 git commit 之前自动执行。**先跑第0项构建测试上下文**，再按下表执行 ①②③。任何一项不通过则**阻止 commit**。

**执行条件**：

| 任务级别 | 执行项 |
|---------|--------|
| 微型 | 仅 ③ 已有测试回归（不跑⓪）|
| 轻量级 | ⓪(简化) + ③ 已有测试回归 |
| 标准级 | ⓪ + ①②③ 全跑 |
| 重量级 | ⓪ + ①②③ 全跑 |

### 第1项：边界输入测试（临时生成）

针对本次改动的函数/组件/API 自动生成边界测试用例，执行后删除。

1. `git diff --cached --name-only` 获取暂存文件
2. 分析改动中的函数、composable、API handler、Vue 组件
3. 对每个改动点生成临时测试文件（`.test.js` / `test_xxx.py`）
4. 执行测试，收集结果
5. 删除临时测试文件

**测试框架检测**：

| 检测条件 | 使用框架 |
|---------|---------|
| 存在 `vitest.config.*` 或 `vite.config.*`（含 test 配置） | vitest |
| 存在 `jest.config.*` | jest |
| 存在 `pytest.ini` / `pyproject.toml`（含 pytest 配置） | pytest |
| 以上都不存在 | **降级为静态扫描模式**（分析代码中有无参数校验/防御，不执行测试） |

**生成规则 — 前端函数/composable**：

| 参数类型 | 测试值 |
|---------|--------|
| 任意参数 | `null` / `undefined` / `""` |
| 字符串参数 | 超长字符串（10000字符）/ `<script>alert(1)</script>` / `' OR 1=1--` / emoji串（`😀`.repeat(100)）/ 包含换行符 `\n\r` |
| 数值参数 | `0` / `-1` / `NaN` / `Infinity` / `Number.MAX_SAFE_INTEGER` |
| 数组参数 | `[]` / 含 1000 个元素的数组 |
| 对象参数 | `{}` / `null` / 含 `__proto__` 键的对象 |

**生成规则 — 后端 API handler**：

- 必填参数缺失（逐个移除必填字段）
- 参数类型错误（string 传 number、array 传 string）
- 边界值（空 body `{}`、字段值为空字符串、超长字段值）

**生成规则 — Vue 组件 Props**：

- `required` prop 不传
- prop 类型错误（如 Number 类型传 String）
- prop 边界值（空字符串、null、超长文本）

**降级静态扫描模式**（无测试框架时）：

不生成测试文件，改为 `Grep` 搜索改动函数中是否有参数校验：
- 函数入口是否有 `if (!param)`、`typeof` 检查、空值防御
- API handler 是否有请求体校验（如 Pydantic model、Joi schema）
- Vue props 是否有 `validator` 函数或 `required` 声明

扫描到无防御的参数 → 标记为 ✗ 需补充校验。

**业务上下文注入**（来自第0项的"业务边界值"）：

通用模板生成的用例之外，**强制追加**第0项画像中列出的业务边界值作为测试用例：

- 取第0项输出的 `业务边界值` 部分
- 对每个参数的业务边界值序列，逐一生成测试用例
- 用例的预期断言来自第0项 `关键 AC` 中对应衍生场景的预期行为
- 业务边界值的失败优先级**高于**通用模板失败：业务规则错了比代码不健壮严重

输出时区分两类失败：
```
  ✗ [业务] handleDeduct(amount=50, balance=49) — 应阻止扣减并提示余额不足，实际扣减成功
  ✗ [通用] handleDeduct(null) — 未处理空值
```

第0项画像中无业务边界值时（如无关联 AC），仅跑通用模板，输出标注"无业务上下文，仅通用边界测试"。

### 第2项：接口契约测试（静态分析）

通过 `Grep` + `Read` 静态分析检查改动代码的接口使用一致性，不生成测试文件：

| 检查项 | 怎么查 |
|-------|--------|
| Props 必填未传 | `Read` 组件的 `defineProps`，提取 `required: true` 的 prop 名；`Grep` 搜索所有使用该组件的地方，检查是否传了该 prop |
| Emit 无监听 | `Read` 组件的 `defineEmits`，提取事件名列表；`Grep` 搜索父组件中 `<组件名` 的使用处，检查是否有 `@事件名` |
| API 返回值字段错误 | `Read` API 函数的返回类型/结构；`Grep` 搜索调用该 API 的代码，检查是否访问了返回值中不存在的字段 |
| Composable 返回值不一致 | `Read` composable 的 return 语句；`Grep` 搜索调用方的解构，检查是否解构了不存在的变量名 |

**业务上下文注入**（来自第0项的"上下游"和"关键 AC"）：

通用契约检查之外，**追加业务字段语义检查**：

| 业务契约项 | 怎么查 | 数据来源 |
|-----------|-------|---------|
| 状态枚举一致性 | 改动代码中出现的 status/state 值是否在 PRD 定义的枚举范围内（如 PRD 定义 status 只有 `pending/paid/cancelled`，代码不能出现 `processing`）| AC 原文中的状态描述 |
| 金额/数值单位一致性 | 改动代码涉及金额时，单位是否与上游传入一致（元/分、整数/浮点）| 第0项的"上游"调用方代码签名 |
| 角色/权限字段语义 | 改动代码中读取 role/permission 字段时，对比值是否与 PRD 定义的角色集合一致 | AC 原文中的角色描述 |
| 业务字段必填 | PRD 定义"必须包含 X 字段"的接口，改动代码的请求/响应是否包含 | AC 原文中的字段约束 |

**示例**：
```
  ✗ [业务] src/store/order.js:23 — status 赋值为 'processing'，PRD 仅定义 pending/paid/cancelled
  ✗ [业务] src/api/credit.js:45 — amount 接收浮点数，上游 CheckoutPage.vue:67 传入的是分（整数）
```

第0项画像中无关联 AC 时，仅跑通用契约检查。

### 第3项：已有测试回归

如果项目有测试框架配置：
- 执行 `npx vitest run` / `npx jest --passWithNoTests` / `pytest`
- 有 FAIL → 阻止 commit，输出失败详情
- 全 PASS → ✓ 通过

如果没有测试框架：
- 跳过，输出"项目无测试框架，仅执行了边界测试"

### commit 测试输出格式

```
[测试] commit 前置测试

  ⓪ 测试上下文：[已构建 N 条业务边界值 + M 条历史坑 / 简化模式 / 跳过]
  [✓/✗] 边界输入测试：N 用例（业务 X / 通用 Y），M 通过
     ✗ [业务] handleDeduct(amount=49, balance=50) — 应提示余额不足，实际扣减成功
     ✗ [通用] handleSubmit(null) — 预期抛错，实际 TypeError 未捕获
  [✓/✗] 接口契约：N 项检查（业务 X / 通用 Y）
     ✗ [业务] src/store/order.js:23 — status 赋值超出 PRD 枚举范围
     ✗ [通用] <UserCard> 必填 prop "userId" 在 Profile.vue:12 未传
  [✓/✗] 已有测试回归：N 通过 / M 失败 / 无测试框架

结论：[全部通过 → 继续 commit] / [N 项失败 → 阻止]
```

**[业务] 类失败优先级高于 [通用]**：业务规则错了说明实现偏离 PRD，必须修；通用类失败可能是边界容错不足，根据严重程度决定。

**失败后处理**：输出"测试反馈"（见下方"测试问题反馈链路"章节），按问题分类引导处理。修复后重新执行安全检查 + commit 前置测试。

## commit 后置文档同步

**触发时机**：**每次 git commit 成功后**自动执行，无论是否走了 `/dev` 流程。确保微型任务、不走流程的改动也能同步到文档。

### 待办事项状态定义

`05-todo.md` 中的任务使用以下状态：

```
需求任务状态：
  ○ 未开始     — 初始状态
  ◐ 进行中     — /dev start 或 commit 关联了该 REQ
  ◉ 已完成     — /dev done 通过 或 commit 表明完成
  ✓ 已验收     — /review check 验收通过
  ⚠ 停滞      — 连续 3 次 push 无变化（健康扫描自动标记）
  ✗ 已放弃     — 操作员手动决定

健康扫描追加项状态：
  🐛 待修复    — 扫描发现的 bug
  🐛✓ 已修复   — 下次扫描检测到已修复
  💡 待处理    — 优化建议
  💡✓ 已处理   — 操作员采纳并实现
  💡— 已忽略   — 操作员决定不做
```

### 执行步骤

1. **解析 commit 信息**：
   - 从 commit message 中提取关联的 REQ-ID（格式：`feat(REQ-A-001):`）
   - 从 `git diff --name-only HEAD~1 HEAD` 获取本次改动的文件列表
   - 如果没有 REQ-ID，尝试通过 `tracemap.json` 根据改动文件反查关联的 REQ

2. **逐文档同步检查**：

#### 2.1 `05-todo.md` — 任务状态同步

- 读取当前 `05-todo.md`
- **有 REQ-ID 关联时**：
  - 任务状态为"○ 未开始" → 更新为"◐ 进行中"
  - commit message 表明功能完成（如 `feat(REQ-A-001): 完成XX`） → 更新为"◉ 已完成"
  - commit message 包含 `refine(N):` → 标记为"◐ 进行中（迭代 N）"
- **通过 tracemap 关联时**（无显式 REQ-ID 但改动文件能关联到任务）：
  - 任务状态为"○ 未开始" → 更新为"◐ 进行中"
- **都关联不上时**：
  - 在 todo 末尾记录"未关联 commit：[hash] [message]"，不改任何状态

#### 2.2 `03-features.md` — 功能实现状态同步

- 根据改动文件，通过 `tracemap.json`（如存在）找到关联的功能点
- 检查关联功能在 `03-features.md` 中的状态
- 如果功能对应的验收标准已全部满足但状态仍为"未实现" → 更新为"已实现"
- 如果功能只有部分实现 → 标注"部分实现：N/M 验收标准通过"

#### 2.3 `02-prd.md` — 边界一致性检查

- 读取 `02-prd.md` 中与本次 commit 关联的需求范围
- 对比本次改动的实际内容：
  - 改动是否超出该需求定义的边界 → 输出**边界溢出提醒**
  - 需求中定义但本次未涉及的部分 → 输出**遗漏提醒**（仅提醒，不阻止）
- 此步骤**只检查不修改** `02-prd.md`，PRD 变更只能通过 `/req update` 执行

#### 2.4 `04-user-guide.md` — 操作说明补全检查

- 检查本次 commit 涉及的功能是否已在 `04-user-guide.md` 中有对应说明
- 如果功能已实现但操作说明缺失 → 输出提醒："[REQ-ID] 功能已实现，操作说明待补充"
- 此步骤**只提醒不自动补写**，操作说明需人工确认内容准确性

#### 2.5 `tracemap.json` — 需求↔代码映射更新

- 根据本次 commit 的改动文件和关联 REQ-ID，更新映射关系
- 新增文件 → 追加映射
- 删除文件 → 移除映射
- 重命名/移动 → 更新路径

### 同步输出格式

```
[文档同步] commit 后置同步 | [commit hash 前7位]

关联需求：[REQ-IDs]
改动文件：[N 个]

  [✓/⚠] todo.md：[已同步 / 状态已更新为"已完成"]
  [✓/⚠] features.md：[已同步 / REQ-A-001 状态更新为"已实现"]
  [✓/⚠] prd.md 边界检查：[一致 / 检测到边界溢出]
  [✓/⚠] user-guide.md：[已有说明 / REQ-A-001 操作说明待补充]
  [✓/⚠] tracemap.json：[已同步 / 新增 N 条映射]

文档同步完成。[如有⚠项请关注]
```

### 规则

- **自动更新**的文档：`05-todo.md`、`03-features.md`、`tracemap.json`
- **只检查提醒**的文档：`02-prd.md`、`04-user-guide.md`
- commit message 中无 REQ-ID → 通过 tracemap 反查改动文件关联的任务；都关联不上则记录"未关联 commit"
- push 前如果有多个未同步的 commit → 批量同步，按 commit 顺序依次执行
- **轻量级任务**：commit 后跳过文档同步，延迟到 push 时一次性执行（减少中间等待）
- **微型任务**（不走 /dev）：commit 后依然执行文档同步，确保 todo 不脱节

## push 前置测试

**触发时机**：git push 之前自动执行。**先复用或重建测试上下文（第0项画像）**，再按下表执行 ④⑤⑥。任何一项不通过则**阻止 push**。

**第0项画像复用规则**：
- 检查 `.skills/{product}/test-context-cache.json` 是否存在且距生成时间 < 10 分钟 → 复用
- 否则重新跑第0项，喂给 ④⑤⑥
- 微型任务跳过第0项（不跑 push 测试）

**执行条件**：

| 任务级别 | 执行项 |
|---------|--------|
| 微型 | 不执行 push 前置测试 |
| 轻量级 | ⓪(简化或复用) + ⑥ 极端环境检查 |
| 标准级 | ⓪(复用或重建) + ④⑤⑥ 全跑 |
| 重量级 | `/dev done` 时已提前跑 ④⑤⑥（含⓪），push 前对新增 commit 做**增量检查**（重跑⓪获取新画像 + 仅检查新增/改动的文件）|

### 第4项：E2E 用户场景测试（半持久，Playwright）

**执行时按需 Read `references/push-tests.md` 的第4项章节获取完整规则。**

要点：需 Playwright + dev server，失败或不可用时输出 `[跳过]`；测试文件位置 `.skills/{product}/tests/e2e/`，页面改动时重生成、未改动时复用；场景覆盖正常流程 / 极端操作（重复提交、超长文本、XSS、后退刷新）/ 异常状态（未登录、404、Token 过期）。输出格式 `[E2E] 用户场景测试 — N 个场景` 含通过/失败/跳过计数。

**业务上下文注入**（来自第0项的"关键 AC"和"业务语义"）：
- 在通用场景之外，**追加业务链路场景**：从第0项 `关键 AC` 提取的"正常路径/边界路径/异常路径"序列，串成完整的端到端流程脚本
- 例：AC 定义"加购→下单→扣积分→生成订单"，则生成完整链路 E2E（含中间态校验：加购后是否进购物车、扣积分后余额是否正确、订单生成后状态是否为 pending）
- 业务链路场景失败优先级高于通用场景，输出标注 `[业务链路]`

### 第5项：API 安全测试（临时生成，node 脚本执行）

**执行时按需 Read `references/push-tests.md` 的第5项章节获取完整测试矩阵与输出格式。**

要点：后端未启动时跳过；Grep 提取端点 → 生成 node fetch 临时脚本 → 执行 → 删脚本；覆盖四类测试：认证绕过（401/403）、注入攻击（SQL/XSS/路径遍历）、参数篡改（userId/权限字段/`__proto__`）、过载防御（超大 body/超长字段）。输出格式 `[API 安全] N 个端点 × M 项检查` 含通过/失败/跳过计数。

**业务上下文注入**（来自第0项的"上下游"和"关键 AC"）：
- 通用安全测试之外，**追加业务权限测试**：
  - 角色边界：用 A 角色 Token 访问 B 角色专属接口（基于 AC 中定义的角色权限矩阵）
  - 资源归属：用户 X 操作用户 Y 的资源（如 `PUT /api/orders/{id}` 改他人订单）
  - 业务状态机：违反状态流转规则（如已支付订单再次支付、已取消订单尝试发货）
- 业务权限失败属于**设计缺陷**类，按"测试问题反馈链路"分类处理

### 第6项：极端环境检查（静态扫描）

**执行时按需 Read `references/push-tests.md` 的第6项章节获取完整检查表与输出格式。**

**不执行代码**，仅用 `Grep` + `Read` 静态扫描改动文件是否有对应防御机制。5 类防御：
- **网络异常**：API 调用无 timeout（中等）/ catch 块无用户提示（中等）/ 无重试机制（建议）
- **并发**：提交按钮无防重复（中等）/ 高频操作无节流（建议）
- **存储**：localStorage 操作无 try-catch（中等）
- **大数据量**：列表无分页/虚拟滚动（建议）/ 图片无懒加载（建议）
- **Token/鉴权**：Token 过期无处理（严重）/ 路由守卫不完整（严重）

严重级别：严重（必修） / 中等（建议修复） / 建议（可选）。输出格式 `[极端环境] 防御机制检查 — N 项`，按 5 类分组汇报通过/失败清单。

**业务上下文注入**（来自第0项的"副作用方向"和"历史坑"）：
- **业务并发防御**：第0项标注的副作用为"写库"或"状态变更"时，检查改动代码是否有：
  - 同一用户对同一资源的并发操作锁（如悲观锁/乐观锁/Redis 锁）
  - 状态机的并发流转是否有原子性保护
- **历史坑回归扫描**：第0项 `历史坑` 中的每条记录，对应到当前改动检查是否仍存在该模式（如曾发生"流水未写入但扣减成功"，本次扫描确认事务边界是否包含流水写入）
- 历史坑命中失败标注 `[历史坑回归]`，必修

### push 测试总输出

```
[测试] push 前置测试

  ⓪ 测试上下文：[复用 commit 时画像（N 分钟前）/ 重新构建 / 简化模式]
  [✓/✗/—] E2E 场景测试：N 场景（业务链路 X / 通用 Y），M 通过
     ✗ [业务链路] 加购→下单→扣积分链路：扣积分后余额未刷新
  [✓/✗/—] API 安全测试：N 端点 × M 项（业务权限 X / 通用 Y）
     ✗ [业务权限] PUT /api/orders/:id 允许跨用户改单
  [✓/✗] 极端环境检查：N 项（含历史坑回归 K 条）
     ✗ [历史坑回归] 扣积分流程未在事务内写流水（曾发生 2026-04-02）

结论：[全部通过 → 继续 push] / [N 项失败 → 阻止]
```

**失败后处理**：输出"测试反馈"（见下方"测试问题反馈链路"章节），按问题分类引导处理。修复后重新执行 push 前置测试。

## 测试问题反馈链路

**适用范围**：commit 前置测试和 push 前置测试中发现的所有失败项。

### 问题分类标准

| 问题类型 | 判断标准 | 处理方式 |
|---------|---------|---------|
| **代码 Bug** | PRD 有定义但实现有缺陷（如"应返回401实际返回200"） | 直接输出位置+原因，开发者修复后重新测试 |
| **业务规则违反** | 第0项业务上下文衍生的测试失败（业务边界值、业务字段语义、业务链路、业务权限、历史坑回归） | 直接修复（PRD 已隐含规则）；如规则本身存疑，升级为需求盲区由操作员裁决 |
| **需求盲区** | PRD 没覆盖的场景（如"空值输入时应该怎样"没定义） | 反馈给操作员决定 → `/req update` 补充 AC → 重新实现 |
| **设计缺陷** | 架构/安全层面漏洞（如"接口无鉴权"、"无防重提交"） | 反馈给操作员标记严重级别 → 确认后作为新任务 `/dev start` |

### 分类判断逻辑

```
测试失败 →
  ├─ 是第0项业务上下文衍生的失败？（标注 [业务]/[业务链路]/[业务权限]/[历史坑回归]）
  │   ├─ 是 → 业务规则违反（PRD 已隐含规则，直接修；存疑则升级为需求盲区）
  │   └─ 否 → 继续判断
  │
  ├─ PRD 验收标准中有明确定义该行为？
  │   ├─ 是 → 代码 Bug（实现不符合 PRD）
  │   └─ 否 → 继续判断
  │
  ├─ 属于通用安全/架构规范？（鉴权、防注入、防重提交等）
  │   ├─ 是 → 设计缺陷
  │   └─ 否 → 需求盲区
```

### 输出格式

```
[测试反馈] 发现 N 个问题需要决策

  🐛 代码Bug（可直接修）：
    1. src/api/auth.js:23 — 无 Token 返回 200，PRD AC-2 要求返回 401
    2. src/components/Form.vue:45 — handleSubmit(null) 未捕获 TypeError

  📋 需求盲区（PRD 未覆盖，需补充）：
    3. 用户输入超过500字时应该截断还是提示？PRD 未定义
    4. 网络断开时表单已填数据是否需要本地缓存？PRD 未定义

    → 请告知处理方式：
      a. 补充到 PRD（/req update）
      b. 暂不处理（跳过该测试项）
      c. 按以下规则处理：[操作员指定]

  🔴 设计缺陷（需要新任务）：
    5. GET /api/users/:id 无鉴权，任何人可访问 — 严重
    6. 删除操作无二次确认 — 中等

    → 是否立即处理？建议走 /dev start

  ────────────────
  代码Bug：直接修复后重新测试
  需求盲区：等操作员决策后继续
  设计缺陷：操作员确认后作为新任务处理
```

### 反馈后的流转

| 问题类型 | 操作员决策后 | 下一步 |
|---------|------------|--------|
| 代码 Bug | — | 直接修复 → 重新跑测试 |
| 需求盲区 | 补充到 PRD | `/req update` 补 AC → 实现 → 重新跑测试 |
| 需求盲区 | 暂不处理 | 标记该测试项为"已知跳过"，记录到 guard log，继续 commit/push |
| 需求盲区 | 按指定规则处理 | 实现 → 重新跑测试 |
| 设计缺陷 | 立即处理 | `/dev start` 新任务 → 完成后回到原任务继续 |
| 设计缺陷 | 延后处理 | 写入 `05-todo.md` 待办，标记严重级别，继续当前 commit/push |

**"已知跳过"的记录**：

操作员决定暂不处理的需求盲区/设计缺陷，记录到 `.skills/guard/{product}.log`：

```
[YYYY-MM-DD HH:MM] TEST_SKIP | [来源测试项] | [严重程度]
  描述：[问题描述]
  操作员决策：暂不处理
  原因：[操作员给出的理由]
```

## push 后置：项目健康扫描

**触发时机**：每次 git push 成功后自动执行。扫描结果写入 `05-todo.md` 的"健康扫描"章节。

### 扫描内容（轻量三检）

> Bug 级代码质量扫描、架构问题、性能优化等深度检查由 `/health scan` 负责，push 扫描只做轻量快检。

#### 1. 标记注释清理

扫描代码中的 `TODO`、`FIXME`、`HACK`、`BUG` 注释，统计数量和位置。

#### 2. 停滞任务检测

- 读取 `05-todo.md`，找出状态为"进行中"超过 3 次 push 未变化的任务 → 标记为停滞
- 读取阶段进度（已完成 / 总数）

#### 3. 未关联 commit 检测

- 对比本次 push 包含的 commit 涉及的文件与 `tracemap/{product}.json`
- 如果有文件未关联到任何 REQ-ID → 提醒补充关联

### 写入 `05-todo.md`

扫描结果追加到 `05-todo.md` 的末尾"健康扫描"章节：

```markdown
## 健康扫描记录

### [YYYY-MM-DD] push 后扫描

**标记注释**（N 项）：
- 📌 [TODO/FIXME/HACK] [描述] — 位置：[文件:行号]

**停滞任务**（K 项）：
- ⚠ [REQ-ID] [任务描述] — 已停滞 N 次 push

**未关联文件**（M 项）：
- 📎 [文件路径] — 未关联到任何 REQ-ID

**阶段进度**：已完成 X/Y 需求 (Z%)
```

### 输出格式

```
[健康扫描] push 后轻量快检

  📌 标记注释：N 项（TODO X / FIXME Y / HACK Z）
  ⚠ 停滞任务：K 项
  📎 未关联文件：M 项
  📊 阶段进度：X/Y (Z%)

已写入 05-todo.md。深度质量扫描请执行 /health scan。
```

### 规则

- 扫描结果**只追加不覆盖**——历史扫描记录保留，可追溯趋势
- 已修复的 Bug 在下次扫描时自动标记为"✓ 已修复"
- 连续 3 次扫描重复出现的 Bug → 优先级自动提升一级
- 如果扫描无任何问题 → 输出"✓ 项目健康，无新增问题"
- **轻量级任务**：仅扫描本次 push 涉及的变更文件，不做全量扫描；同时执行被延迟的文档同步
