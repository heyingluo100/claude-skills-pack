# 代码可维护性检查清单

/dev done 第3关使用此清单逐项检查。

## 检查项

### 1. 模块边界清晰

**通过条件**：新功能有清晰的模块边界，不与其他模块交叉耦合

**检查方法**：
- 新增的文件是否在正确的目录下
- 是否有直接引用不属于本模块职责的其他模块内部文件
- 模块对外暴露是否通过统一入口（index.js / 公共 API）
- Grep 当前任务新增/修改文件的 import 语句，检查是否存在跨 composable 直接引用（如 useA.js import useB.js 的内部函数）
- 如果存在跨模块引用，判断是否应提取为独立的 shared service（`services/` 目录下）

**典型违规**：登录模块直接引用了订单模块的内部方法

---

### 2. 接口契约明确

**通过条件**：模块对外暴露的接口有明确的输入/输出定义

**检查方法**：
- API 端点是否有请求/响应结构定义
- 组件 Props 是否用 defineProps 定义了类型
- 函数参数和返回值是否有清晰的注释或 JSDoc

**典型违规**：导出一个函数但调用方不知道该传什么参数

---

### 3. 依赖方向合理

**通过条件**：依赖单向，无循环依赖

**检查方法**：
- A 引用 B，B 是否也引用了 A
- 底层模块（utils, repository）是否引用了上层模块（service, controller）
- 对比当前新增的函数体，Grep 项目中是否已有相似实现（相同函数名或相似逻辑 ≥15 行）
- 若发现重复，标记为"应提取"并给出具体建议：提取到哪个文件、暴露什么接口

**典型违规**：A→B→C→A 循环依赖

---

### 4. 副作用可控

**通过条件**：函数/方法的副作用限制在可预期范围内

**检查方法**：
- 数据库写操作是否集中在 service/repository 层
- 是否有意外的全局状态修改
- 异步操作是否有正确的错误处理

**典型违规**：一个工具函数里偷偷修改了全局变量

---

### 5. 配置可外部化

**通过条件**：无硬编码的魔法值

**检查方法**：
- API URL、超时时间、重试次数等是否提取为配置
- 阈值、限制数量等是否作为常量或配置项

**典型违规**：代码中直接写 `setTimeout(fn, 3600000)`

---

### 6. 错误可追踪

**通过条件**：错误处理有足够上下文供排查

**检查方法**：
- catch 块是否只是 `console.log(err)` 而不包含上下文
- 错误信息是否包含：什么操作、什么参数、什么原因
- 是否有静默吞掉错误的 catch

**典型违规**：`catch(e) {}` 空 catch

---

### 7. 可独立测试

**通过条件**：核心逻辑可以独立验证，不依赖完整应用启动

**检查方法**：
- 业务逻辑是否与 UI/框架解耦
- 是否可以直接调用核心函数验证结果
- 数据处理逻辑是否可以用简单输入/输出测试

**典型违规**：所有逻辑都写在 Vue 组件的 onMounted 里，无法脱离组件测试

---

## 评分规则

- 7/7 通过 → ✓ 可维护性检查通过
- 5-6/7 通过 → ⚠ 建议修复后再标记完成
- <5/7 通过 → ✗ 必须修复后再标记完成

## Vue 组件额外检查（来自 Auto-Optimize 评分体系）

适用于 `*.vue` 文件：

| 维度 | 检查点 |
|------|--------|
| 正确性 | 渲染预期输出、props/events 契约正确 |
| 视觉还原 | 遵循 linear-* token、亮暗主题兼容 |
| 集成性 | props/events 与父组件对接正确 |
| 健壮性 | 处理空数据/缺失数据、加载状态 |
| 代码质量 | SFC 顺序正确、ref 不用 reactive、handle* 命名 |
