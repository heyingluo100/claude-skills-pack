# /review — 验收复盘

## 共通规则

1. **不虚报**：没有实际验证的功能不能标记为通过
2. **中文输出**：所有报告用中文
3. **PRD 为准**：验收标准以 PRD 原文为唯一基准，不能自行降低标准

## 前置检查

1. 读取 `.skills/context.json` 获取当前产品
2. **需求文档定位（按优先级依次查找）**：
   - **路线 A — Skill 路线**：操作员**主动**指定 SKILL.md 路径作为验收基准 → 直接以该 SKILL.md 作为验收基准
   - **路线 B — 完整流程**：检查 `02-prd.md` 是否存在 → 存在则使用
   - **都不存在**：提示「未找到需求文档，无法验收。请选择：(A) 指定一个 SKILL.md 路径；(B) 先执行 /req finalize 生成 PRD」，终止执行
3. 检查 `05-todo.md` 是否存在
   - 不存在 → 提示"待办事项文件缺失，验收将仅基于需求文档进行，无法统计任务完成度"，询问是否继续
4. **项目快扫**（仅 `check` / `gap` 子命令、本会话未扫过时执行）：
   - Read `package.json` / `pyproject.toml` / `pom.xml` 任一存在的清单文件
   - Glob 项目主要源码目录（`src/`、`app/` 等）
   - 输出一行：`[项目摸底] 类型:XX | 栈:XX | 主要源码目录:XX → 继续`
   - 摸底结果决定验收侧重点：Vue 项目检查响应式/组件结构，Python 检查异常处理，Java 检查日志埋点
   - `summary` 子命令不需要扫（只汇总文档）

---

## 子命令路由

| 参数 | 执行 |
|------|------|
| `check` | → 逐条验收（单个需求或整个阶段） |
| `check [REQ-ID]` | → 验收指定需求 |
| `check --phase [N]` | → 验收整个阶段 |
| `gap` | → 需求与实现的差距分析 |
| `summary` | → 项目复盘总结 + README 更新 |
| 无参数 | → 显示验收概览 |

### 自然语言路由

当操作员使用自然语言而非精确命令时，按以下规则映射：

| 操作员可能的表达 | 映射到 |
|---|---|
| "验收一下"、"检查完成度" | → check |
| "差距分析"、"还差多少" | → gap |
| "做个复盘"、"总结一下" | → summary |

## check — 验收检查

### 执行步骤

1. **确定验收范围**：
   - 指定 REQ-ID → 验收单个需求
   - `--phase N` → 验收该 阶段下所有需求
   - 无参数 → 验收所有已标记为"已实现"的需求

2. **逐条对照 PRD 验收标准**：
   - 读取 `02-prd.md` 中对应需求的验收标准
   - 读取 `03-features.md` 中的交互细节和边界情况
   - 逐条验证（优先通过实际运行验证（启动页面、执行功能）；无法运行时，列出具体验证方式请操作员手动确认）

3. **汇总 guard 偏离记录**：
   - 读取 `.skills/guard/{product}.log`
   - 筛选与当前验收范围相关的偏离记录
   - 标注哪些偏离已处理、哪些通过强制跳过

4. **输出验收报告**

### 验收报告格式

```
[REVIEW CHECK] 验收报告

产品：[产品名] | PRD：v[版本] | 验收范围：[REQ-ID / 阶段 N]

━━━ 验收结果 ━━━

REQ-A-001 邮箱密码登录 [基础 | 阶段一]
  ✓ AC-1：正确凭证登录成功跳转首页
  ✓ AC-2：错误密码显示统一错误信息
  ✗ AC-3：连续失败触发锁定机制 — 未实现
  结论：2/3 通过 → 未通过

REQ-A-003 注册 [基础 | 阶段一]
  ✓ AC-1：邮箱注册成功
  ✓ AC-2：邮箱验证链接有效
  结论：2/2 通过 → ✓ 通过

━━━ Guard 偏离记录 ━━━

本次验收范围内的偏离：2 条
  [已处理] IMPL_DRIFT | REQ-A-001 | 已修正
  [强制跳过] SCOPE_CREEP | REQ-A-002 | 原因：客户需要

━━━ 统计 ━━━

验收通过：1/2 需求
验收标准通过率：4/5 (80%)
Guard 偏离：2 条（1 已处理、1 强制跳过）
```

### 验收通过后的联动

当一个需求验收通过时，自动执行：

1. **更新 `05-todo.md`**：
   - 该需求标记为"✓ 已完成"
   - 子项"review check 验收通过"打勾

2. **更新 `04-user-guide.md`**：
   - 补充该功能的用户操作说明
   - 按功能书中的交互细节编写

3. **更新 `03-features.md`**：
   - 该功能状态从"已实现"改为"已验收"

4. **输出同步确认**：
```
[SYNC] 验收通过联动：
  ✓ todo.md — REQ-A-003 标记完成
  ✓ user-guide.md — 注册功能操作说明已补充
  ✓ features.md — FEAT-A-003 状态更新为"已验收"
```

5. **持久化验收报告**：将本次验收结果写入 `.skills/{product}/docs/review-{YYYY-MM-DD}.md`，格式与对话输出一致。如果同日已有文件则追加（用分隔线隔开）。

### Skill 元开发轨追加检查（仅当 plan.md / skill-map.md 存在）

在原有 check 流程之外，如检测到当前是 Skill 元开发轨场景（`.skills/{product}/docs/plan.md` 和 `skill-map.md` 都存在），追加以下检查项：

1. **plan + skill-map 三方对照**：
   - PRD 中的 REQ 是否在 `skill-map.md` 中存在
   - 是否标明适合做 skill；不适合时原因是否合理
   - 适合做 skill 的，是否有 skill 名称、类型、输入、输出、验收方式
   - 对应 `.claude/skills/{name}/SKILL.md` 是否存在
   - SKILL.md 是否覆盖输入、输出、流程、边界、错误处理

2. **蓝本侦察检查**：
   - `plan.md` 是否标记需要 `/github-blueprint` 但没有蓝本报告、跳过记录或联网失败原因
   - 轻量单 skill 是否有本地查重记录
   - 蓝本报告是否包含许可证处理和本项目适配方式（不能把外部蓝本当权威源）
   - 默认不因缺少蓝本报告阻塞验收；plan 明确要求时缺少报告列为中等风险

3. **拆分与编排检查**：
   - 复杂需求是否选择了合理编排方式：主 skill / scripts 串接 / plan.md+skill-map.md 编排表
   - skill 流程是否超过 10 步、职责是否混杂、是否包含多个状态阶段（疑似压成单体）
   - 是否存在本应拆分但被压成单体的风险（中间产物有价值、需要确认、前后阶段评估方法不同等）
   - 主 skill 编排时，主 skill 是否只做顺序/确认/状态衔接，不复制子 skill 业务逻辑

4. **实现承载追踪**：
   - 如果 plan 或 PRD 标记需要实现承载，功能能否追溯到 REQ；字段、接口、状态、报告结构、命令参数或数据流没有绕过 PRD/plan/skill-map/SKILL.md
   - 如果系统/页面/API/CLI/脚本/数据处理/报告产物已发生功能变化，PRD、features、plan、skill-map、SKILL.md 是否同步
   - 是否提供按类型的工程验收证据（页面无白屏/报错；API 契约和错误响应；CLI/脚本参数和退出码；数据样例；报告结构和证据追溯；构建/测试/运行验证记录）

5. **质量证据检查**：
   - 是否经过 `/darwin-skill` 优化或至少有评分记录
   - 核心/高风险/编排型 skill 是否有 `/eval-skill` 实证评估证据
   - 测试 prompt 是否仍匹配 skill 当前用途（不可过期）

6. **skill-map 状态推进**：
   - 通过项 → 把 `skill-map.md` 中对应条目状态推进为 `reviewed`
   - 不通过项保持原状态，并在 review 报告中写明原因
   - 不回退已是 `packed` 的条目
   - 状态更新前在报告中展示影响预览

## gap — 差距分析

分析需求与实现之间的整体差距。

### 执行步骤

1. 读取 `02-prd.md` 所有需求
2. 读取 `05-todo.md` 所有任务状态
3. 读取 `.skills/tracemap/{product}.json`（如存在）
4. 对比分析

### 输出格式

```
[REVIEW GAP] 差距分析

阶段一(MVP)：
  已验收：8/12 需求 (67%)
  已实现未验收：2/12 需求
  未实现：2/12 需求
    - REQ-B-002 数据搜索 — 未开始
    - REQ-B-003 数据导出 — 未开始

阶段二(增强)：
  全部未开始（0/8）

孤立代码（有代码但无需求关联）：
  - src/utils/legacy-helper.js — 未关联任何 REQ

孤立需求（有需求但无代码关联）：
  - REQ-C-004 数据归档 — 阶段二（正常，尚未开发）

Baseline 对齐：
  痛点1 "注册繁琐"：3 个功能覆盖 ✓
  痛点2 "导出单一"：0 个功能覆盖 ⚠（阶段一的 REQ-B-003 未完成）
  痛点3 "查询慢"：2 个功能覆盖 ✓
```

## summary — 项目复盘

在一个 阶段完成后或项目整体完成后使用。

### 执行步骤

1. 汇总当前阶段的所有验收结果
2. 汇总所有 guard 偏离记录和强制跳过
3. 汇总需求变更历史（changelog）
4. 生成复盘报告
5. **输出 README 更新预览**：在写入前，先将即将新增或修改的内容以 diff 或对照形式展示给操作员，等操作员确认后再执行写入。

6. **检查并更新 README.md**：
   - 不存在 → 创建（项目简介、技术栈、启动方式、目录结构、部署说明）
   - 已存在 → 根据本 阶段的新增功能更新

### 输出格式

```
[REVIEW SUMMARY] 项目复盘 — 阶段一

━━━ 完成情况 ━━━
阶段一需求：12 个
已验收通过：12 个 (100%)
总验收标准：38 条，全部通过

━━━ 质量回顾 ━━━
Guard 偏离总计：5 条
  功能蔓延：2 条
  实现偏差：2 条
  方向偏离：1 条
  其中 强制跳过：1 条（原因：客户 demo 需要）

需求变更总计：3 次
  v1.0 → v1.1：REQ-A-002 提前到阶段一
  v1.1 → v1.2：REQ-B-003 导出格式变更
  v1.2 → v1.3：新增 REQ-D-001 移动适配

━━━ 下一步 ━━━
阶段二待开发需求：8 个
建议优先：[REQ-IDs]

━━━ README ━━━
[✓ 已创建/更新] README.md
```

## 与其他 Skill 的协同

| Skill | 协同方式 |
|-------|---------|
| `/dev done` | 验收是 dev done 之后的正式环节（研发产品轨） |
| `/guard` | 验收时汇总所有偏离记录（研发产品轨） |
| `/req` | 验收基于 PRD 验收标准 |
| `/plan` | 元开发轨：基于 plan.md 和 skill-map.md 验收 skill 覆盖度 |
| `/github-blueprint` | 元开发轨：检查蓝本报告、跳过记录或联网失败原因 |
| `/create-skill` | 元开发轨：验证 skill 创建产物 |
| `/darwin-skill` | 元开发轨：检查是否有评分记录 |
| `/eval-skill` | 元开发轨：检查核心/高风险 skill 是否有实证评估证据 |
| `/pack` | 元开发轨：reviewed 通过后由 /pack build 推进到 packed |
| `/prompt-log` | 复盘时建议保存有效的沟通模式 |

## 状态更新规则

`/review` 只更新 `.skills/{product}/docs/` 下的文档（review 报告、todo、user-guide、features）和（元开发轨）`skill-map.md`。

不自动改：

- `README.md`（仅 `summary` 子命令更新，且需操作员确认 diff）
- `CLAUDE.md`、`AGENTS.md`
- `pack-manifest.json`
- 任何 `SKILL.md`

如果发现需要改这些文件，输出建议，等用户确认后交给对应流程。

`/review` 只能把验收通过项更新为 `reviewed`，不得回退 `packed`。对不通过项保持原状态，并在报告中写明原因。
