# /req — 需求分析与 PRD 管理

## 共通规则（所有子命令执行前必须遵守）

1. **反问优先**：如果用户提供的信息不够详细，必须反问补充，不自行脑补需求
2. **先说后做**：执行前先告知简要方案和想法，确认后再动手
3. **中文输出**：所有文档和交互用中文
4. **阶段门禁**：前一阶段未完成不进入下一阶段，用户确认后才推进。执行阶段命令时，先读取 `context.json` 的 `stage` 字段检查：
   - `position` 需要 stage ≥ 1（init 后自动为 1）
   - `user` 需要 stage ≥ 2（position 完成后更新为 2）
   - `compete` 需要 stage ≥ 3
   - `feature` 需要 stage ≥ 4
   - `priority` 需要 stage ≥ 5
   - `finalize` 需要 stage ≥ 6
   - 不满足时输出：`[REQ] 当前处于阶段 {stage}，请先完成阶段 {需要的阶段} 再执行此命令。` 并终止
   - 每个阶段完成并获用户确认后，更新 `context.json` 的 `stage` 值为下一阶段编号
5. **文档同步**：任何修改操作完成后，按同步规则更新关联文档
6. **需求接收规则**：当操作员提出优化或新需求时，禁止直接执行。必须先自主分析整理（理解重述 → 涉及优化点 → 优化流程 → 功能边界 → 交叉影响 → 风险点），输出后等操作员确认才执行
7. **功能边界意识**：每次变更都要分析对其他已有功能点的影响，不能只关注当前改动点
8. **实现承载同步**：如果需求需要系统、页面、API、CLI、脚本、数据处理、报告工具、状态看板或对外交付承载复杂操作或运行产物，必须把实现承载的 REQ、交付物类型、操作/接口/参数、输入输出、状态、报告字段、验收标准和同步要求写入需求文档；实现变化不能脱离 PRD 和（元开发轨）skill-map。实现承载层只是交付形态，不替代 PRD、plan、skill-map 或 SKILL.md 作为事实源

## 多产品上下文管理

所有子命令执行前，先确定当前产品上下文：

1. 读取 `.skills/context.json`，获取 `activeProduct` 字段
2. 如果不存在或为空，提示用户先执行 `/req init [产品名]` 或 `/req switch [产品名]`
3. 后续所有文件操作基于 `.skills/{activeProduct}/docs/` 目录

`context.json` 结构：
```json
{
  "activeProduct": "产品名",
  "products": {
    "产品名": {
      "createdAt": "YYYY-MM-DD",
      "prdVersion": "v1.0",
      "baselineVersion": "v1.0",
      "phase": "需求分析",
      "stage": 1,
      "source": "new"
    }
  }
}
```

## init — 需求初始化

### 全新产品（`/req init [产品名]`）

执行步骤：

1. 创建目录 `.skills/[产品名]/docs/`
2. 创建/更新 `.skills/context.json`，设置 `activeProduct`
3. 在对话中输出确认信息，然后引导进入阶段1

输出：
```
✓ 已创建产品：[产品名]
✓ 已设为当前活跃产品
✓ 文档目录：.skills/[产品名]/docs/

→ 现在进入阶段1：产品定位
→ 请描述你的产品想法，我会引导你完成需求分析。
```

### 历史继承（`/req init --from [历史产品] [新产品名]`）

执行步骤：

1. **项目快扫**（本会话未扫过时执行）：
   - Read `package.json` / `pyproject.toml` / `pom.xml` 任一存在的清单文件
   - Glob 项目根目录看大致结构
   - 输出一行：`[项目摸底] 类型:XX | 栈:XX | 已有相关:XX/无 → 继续`
   - 摸底结果用于：基于老产品迭代时知道现状，避免提"重新搭建 XX"当项目里已有
2. 读取 `.skills/[历史产品]/docs/` 下的所有文档
3. 输出历史需求摘要（痛点、目标、功能模块、完成状态）
4. 交互式确认迭代类型：
   - a. 痛点不变，优化现有功能
   - b. 新增痛点/目标，扩展功能范围
   - c. 痛点变化，部分需求需要重新定义
   - d. 完全重做（仅参考历史，不继承）
5. 生成 `00-history.md`（使用 `${CLAUDE_SKILL_DIR}/templates/history.md` 模板）
6. 创建新产品目录，设置 context
7. 引导进入阶段1，但每个阶段会自动对比历史需求；每个阶段执行时，自动加载历史文档中对应章节作为参考，并在阶段小结中标注与历史版本的差异点

## 阶段1：产品定位（`/req position`）

引导用户回答以下问题（逐个引导，不要一次全问）：

1. **产品背景**：为什么要做这个产品？解决什么问题？
2. **产品愿景**：一句话描述产品的核心价值
3. **业务目标**：可量化的成功指标（如 DAU、转化率、效率提升 %）
4. **边界定义**：这个产品"不是什么"，明确排除项

完成后输出阶段小结，用户确认后记录到 PRD 草稿中。

```
## 阶段1 小结：产品定位

- 背景：[总结]
- 愿景：[一句话]
- 目标：[1-3 个可量化指标]
- 排除项：[不做什么]

→ 确认无误？确认后进入阶段2：用户分析
```

---

## 阶段2：用户分析（`/req user`）

引导用户回答：

1. **目标用户画像**：谁是主要用户？谁是次要用户？
2. **用户场景**：用户在什么情境下使用？
3. **用户痛点**：当前用户的核心问题（按严重程度排序）
4. **用户旅程**：从接触到完成核心任务的路径

完成后同样输出阶段小结，用户确认后推进。

---

## 阶段3：竞品调研（`/req compete`）

引导用户讨论：

1. **竞品清单**：直接竞品 + 间接竞品
2. **功能对比矩阵**：各竞品核心功能有无对比
3. **优劣势分析**：竞品做得好/差的地方
4. **差异化机会**：我们可以在哪里做出差异

如果用户不了解竞品情况，主动搜索相关信息辅助分析。

---

## 阶段4：功能拆解（`/req feature`）

这是颗粒度最细的阶段。引导用户逐模块拆解：

**推荐先做项目快扫**（本会话未扫过且项目里有现成代码时）：
- Read `package.json` / 主要配置文件
- Glob `src/` 或主要源码目录
- 输出一行：`[项目摸底] 类型:XX | 已有功能:XX → 继续`
- 知道现有功能后，拆解时能区分"新增"和"扩展已有"，避免重复造轮子

1. 先梳理功能模块（按业务域）
2. 每个模块下枚举功能点
3. 每个功能点拆为三级：
   - **基础** — 满足核心场景的最小可用功能
   - **增强** — 提升体验/效率的增强功能
   - **高级** — 面向特殊场景的扩展功能

4. 每个功能点必须包含：
   - 功能描述（一句话）
   - 用户故事（作为[角色]，我想要[功能]，以便[价值]）
   - 验收标准（怎样算"做完了"）
   - 边界情况（异常输入、极端场景）

5. 为每个功能点分配编号：`REQ-[模块字母]-[序号]`

6. **实现承载识别**（仅复杂需求需要时）：判断哪些 REQ 需要系统、页面、API、CLI、脚本、数据处理、报告工具、状态看板或对外交付承载。对需要承载的 REQ，在功能书中追加记录：
   - 交付物类型：系统 / 页面 / API / CLI / 脚本 / 数据处理 / 报告工具 / 其他
   - 使用者：谁来用、谁来调用
   - 用户操作或调用方式：UI 操作流 / 接口签名 / 命令参数 / 数据流
   - 关键状态：处理中、成功、失败、空态、异常
   - 输入输出：读取哪些文件、接口或状态；是否写回事实源
   - 结果字段：报告结构、响应字段、数据样例
   - 验收标准：按类型说明 UI/API/CLI/数据/报告/安全/构建/测试证据
   - 事实源边界：哪些字段、状态变化必须同步回 PRD、plan、skill-map 或相关 SKILL.md
   
   **不适合实现承载提醒的场景**：简单 skill、单点文案/配置、纯 markdown 方案、内部规则讨论、一次性命令检查或打包。

如果用户描述模糊，必须追问直到每个功能点的验收标准明确。

---

## 阶段5：需求分级（`/req priority`）

基于阶段4的功能拆解，引导分级：

1. 按 MoSCoW 法则分级每个功能点：
   - 必须有（MVP 核心功能）
   - 应该有（强烈期望有）
   - 可以有（有了更好）
   - 暂不做（本期不做）

2. 规划迭代：
   - 阶段一（MVP）：仅"必须有"的基础功能
   - 阶段二（增强）："必须有"的增强功能 + "应该有"
   - 阶段三（扩展）："可以有" + 高级功能

3. 标注依赖关系：哪些功能必须先做

输出迭代规划表：

```
| 需求编号 | 功能点 | 模块 | 分级 | 迭代 | 依赖 |
|---------|--------|------|------|------|------|
```

---

## 阶段6：定稿（`/req finalize`）

生成完整的基础文档集。依次执行：

1. **一致性校验**：
   - 所有功能点是否都有验收标准
   - 所有"必须有"是否都在阶段一中
   - 是否存在没有用户故事的功能点
   - 依赖关系是否有循环
   - 需求编号是否连续无遗漏

2. **生成 5 个文档**（读取 `${CLAUDE_SKILL_DIR}/templates/` 下的模板，填充内容后写入）：
   - `01-baseline.md` — 冻结需求基线（写入后不再修改）
   - `02-prd.md` — 完整 PRD
   - `03-features.md` — 功能书
   - `04-user-guide.md` — 操作指南（初始版，仅快速开始章节）
   - `05-todo.md` — 待办事项（全流程追踪）

   模板文件清单（`${CLAUDE_SKILL_DIR}/templates/`）：
   - `baseline.md` → 生成 `01-baseline.md`
   - `prd.md` → 生成 `02-prd.md`
   - `features.md` → 生成 `03-features.md`
   - `todo.md` → 生成 `05-todo.md`
   - `user-guide.md` → 生成 `04-user-guide.md`
   - `history.md` → 生成 `00-history.md`（仅继承项目）

   **模板降级**：如果模板文件不存在（`${CLAUDE_SKILL_DIR}/templates/` 目录缺失或模板文件缺失），按以下方式降级：
   - 基于阶段 1-5 收集的信息，直接生成文档内容（不依赖模板格式）
   - 输出提醒：`[REQ] 模板文件缺失，已使用内置格式生成文档。建议恢复模板文件以保持格式一致性。`
   - 生成的文档必须包含与模板相同的核心章节（需求基线必须有痛点/目标/边界，PRD 必须有版本号/REQ 编号/验收标准）

3. 如果是历史继承项目，额外生成 `00-history.md`

4. 创建 `.skills/changelog/[产品名].log`

5. 更新 `context.json` 中的 `prdVersion` 和 `phase`

6. 输出文档生成确认：
```
✓ 基础文档集已生成：
  01-baseline.md  — 需求基线（已冻结）
  02-prd.md       — PRD v1.0
  03-features.md  — 功能书
  04-user-guide.md — 操作指南
  05-todo.md      — 待办事项

→ 需求分析阶段完成，可以执行 /plan create 进入方案设计
```

## update — 更新需求（`/req update [模块]`）

**项目快扫**（本会话未扫过时，update 必须执行）：
- Read 主要清单文件 + Glob 项目根目录结构
- 操作员需求里有具体功能词 → Grep 在 src/ 下定位是否已有实现
- 输出一行：`[项目摸底] 类型:XX | 栈:XX | 已有相关:XX/无 → 继续`
- 摸底结果用于：知道改动现状，判断"是改已有"还是"新增"，影响偏差检测的准确性

**每次更新前自动执行三层偏差检测：**

### 第1层：Baseline 对比（初心偏差）

读取 `01-baseline.md`，检查本次变更是否偏离原始痛点和目标。

### 第2层：当前 PRD 对比（范围偏差）

读取 `02-prd.md`，检查本次变更是否超出/缩小已定义范围。

### 第3层：历史继承对比（继承偏差）— 仅迭代项目

读取 `00-history.md`（如存在），检查是否破坏继承的功能契约。

### 偏差报告格式

```
[REQ UPDATE - 偏差检测] 模块：[模块名]

更新内容：[描述]
变更类型：功能增强 / 功能替换 / 功能删除 / 排期调整

偏差检测结果：
  [✓/⚠/✗] 第1层 Baseline：[结论]
  [✓/⚠/✗] 第2层 PRD：[结论]
  [✓/⚠/✗] 第3层 历史继承：[结论]（仅迭代项目）

结论：[无偏差 / 检测到 N 项偏差]
```

偏差类型判定：
- **初心偏差**（高）：偏离 baseline 核心痛点/目标 → 必须停下讨论
- **范围偏差**（高）：超出/缩小 PRD 范围 → 需正式更新
- **继承破坏**（高）：破坏历史继承契约 → 需修改继承状态
- **波及偏差**（中）：间接影响其他需求 → 接受但需同步更新
- **渐进偏差**（中）：累计小变更导致方向漂移 → 建议全局回顾
- **正常演进**（无）：合理优化 → 直接通过

### 更新后的文档同步

更新通过后，自动同步：
- `02-prd.md` — 更新对应需求条目，版本号递增
- `03-features.md` — 标记受影响功能；如涉及实现承载相关的字段/接口/状态/数据流变化，同步对应承载记录
- `05-todo.md` — 新增/调整任务项
- `.skills/changelog/[产品名].log` — 记录变更详情
- 如当前是 Skill 元开发轨，且存在 `.skills/{产品名}/docs/skill-map.md`：提示需后续执行 `/plan update` 同步 skill-map（本 skill 不直接改 skill-map）

## show — 展示当前需求（`/req show`）

读取 `02-prd.md` 全文输出。如果文件不存在，提示当前阶段进度和已收集的信息。

## status — 需求健康度检查（`/req status`）

读取所有文档，输出健康度报告：
- PRD 版本 + Baseline 版本
- 各阶段需求完成度
- Baseline 对齐情况（核心痛点是否都有功能覆盖）
- 文档同步状态
- 预警项（过期、孤立代码/需求）

## diff — 变更历史（`/req diff`）

读取 `.skills/changelog/[产品名].log` 输出。
支持 `/req diff v1.0 v1.2` 对比指定版本。

## baseline — 查看基线（`/req baseline`）

读取 `01-baseline.md` 全文输出（只读）。
`/req baseline --drift-summary`：对比 baseline 和当前 PRD，分析渐进偏差。

## history — 查看继承关系（`/req history`）

读取 `00-history.md` 输出（仅迭代项目有此文件）。

## switch — 切换产品（`/req switch [产品名]`）

更新 `context.json` 的 `activeProduct`，输出切换确认。

## list — 查看所有产品（`/req list`）

读取 `context.json`，列出所有产品及其状态。
