# /clarify — 模糊需求澄清

## 定位

把模糊需求变成"能分级"的清晰描述，然后交回主流程的「第0步任务分级」。

`/clarify` 只做最小澄清，不产出 PRD、不做方案、不问技术选型、不设计脚本语言。这些分别属于 `/req`、`/plan`、`/create-skill`、`/dev`。

## 触发条件

当用户表达无法判断最终产物或规模时触发，例如：

- "帮我弄个东西"
- "做个工具"
- "优化一下流程"
- "做个数据相关的"
- "搭一套能力"

如果用户需求已经能判断走小功能点、轻量单 skill、复杂需求（双轨）或不适合 skill，则跳过 `/clarify` 直接进入第0步分级。

## 核心问题

第一问固定为：

```text
你最终想要得到什么结果？
```

回答后判断是否足够分级：

- 足够：输出结果，结束。
- 不足：只追问一个最关键缺口。

**硬限制**：最多 2 轮。2 轮仍模糊时，用已有信息给出合理假设，必须标注"我推断"。

## 禁止事项

- 不追问技术栈、目录结构、脚本语言。
- 不在澄清阶段设计 skill 流程或研发方案。
- 不直接写文件。
- 不把复杂需求压成一个超大 skill。

## 分级口径

| 规模预判 | 判断标准 | 建议流程 |
|---|---|---|
| **小功能点** | 1-2 个**研发**功能点，输入输出明确，要的是业务代码 | /create-skill → /dev（研发产品轨轻量路径） |
| **轻量单 skill** | 1-2 个 **skill 元开发**功能点，输入输出明确，不需要多 skill 协作 | /create-skill → /darwin-skill → /eval-skill（按需）→ /review → /pack |
| **复杂需求** | 多功能点、多阶段、多输入输出，需要方案拆解、状态流转或多个 skill 协作 | 走【双轨主链路】决策树（见 CLAUDE.md），先判定研发产品轨 / Skill 元开发轨 |
| **不适合做成 skill** | 持续运行服务、长期 UI、后台队列、登录态、购物车、监控告警等系统能力 | 先拆成可触发的一次性工作流，再判断哪些部分可做 skill |

## 复杂需求命中条件

满足任一条件时，不能走小功能点或轻量单 skill：

- 功能点超过 2 个。
- 涉及多个角色、多个阶段、多个输入输出。
- 需要状态流转、审批、队列、报告、评分、复盘等完整工作流。
- 需要多个 skills 协作完成。
- 用户表达"大平台""全套流程""完整体系""工作台""系统化能力"。
- 边界仍不清楚，需要先拆清楚做什么、不做什么。

## 轻量单 skill 硬限制

- 不允许为了省流程把复杂需求塞进一个 skill。
- 单体流程超过 10 步、职责混杂或需要多个状态阶段时，必须回到 `/plan` 拆分。
- 不在轻量路径里设计平台、服务、持续运行系统。

## 实现承载提醒

`/clarify` 只识别是否需要提醒，不设计系统、页面、API、CLI、脚本、数据处理或报告工具，不问技术栈、不决定目录结构。

当用户最终目标明显包含以下任一特征时，在输出中追加"实现承载建议"：

- 需要交付给他人使用或验收。
- 需要系统、页面、API、CLI、脚本、数据处理、报告工具、状态看板或可运行产物。
- 需要输出结果报告、评审页、展示页、接口结果或批处理产物。
- 用户可操作内容很多，例如批量选择、筛选、参数调整、多轮确认、命令参数或接口调用。
- 多个 skill 的结果需要集中浏览、对比、展开详情、自动处理或长期复用。

以下场景不追加实现承载提醒：简单 skill、单点文案/配置、内部规则讨论、普通 markdown 方案、一次性命令检查。

实现承载提醒必须说明：实现承载层只是系统、页面、API、CLI、脚本、数据处理或报告工具等交付形态，PRD、plan、skill-map 和相关 SKILL.md 仍是事实源；后续实现功能、接口、字段、状态或报告结构变化需要同步回 skills 体系。

## 输出格式

```text
**需求**：[一句话清晰描述]
**规模预判**：小功能点 / 轻量单 skill / 复杂需求 / 不适合做成 skill
**依据**：[为什么这样判断]
**建议流程**：[/create-skill → /dev 或 /create-skill → /darwin-skill → ... 或 走【双轨主链路】决策树]
**实现承载建议**：[不需要 / 建议考虑实现承载：类型 + 原因 + 后续需同步 PRD/plan/skill-map/SKILL.md]
```

如果是推断（2 轮仍模糊后给出假设）：

```text
**我推断**：[推断出的需求]
**依据**：[来自用户描述的证据]
**不确定点**：[仍缺的信息]
**建议流程**：[流程]
```

## 错误兜底

| 场景 | 处理 |
|---|---|
| 用户需求其实清晰 | 跳过澄清，直接交回第0步分级 |
| 2 轮仍模糊 | 标注"我推断"后继续 |
| 用户要做持续服务 | 标记为"不适合直接做成 skill"，建议拆成一次性工作流 |
| 用户要直接开发系统、页面、API、CLI 或脚本 | 说明先经 `/req`、`/plan` 明确事实源、实现类型和验收证据，再决定走哪条轨 |
| 非开发需求 | 告知不在本体系处理范围 |
